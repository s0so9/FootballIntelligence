# Real-data intelligence pipeline with database persistence

The implementation adds a comprehensive data ingestion and persistence layer on top of the existing multi-provider architecture, connecting normalized provider data to a PostgreSQL-compatible database schema, feature engineering, and the prediction engine.

The architecture follows clean boundaries: provider layer → ingestion → database → feature engineering → prediction. xG fields are preserved through the upsert logic, latency tracking correctly handles missing timestamps, and feature extraction prevents data leakage by filtering on `before_datetime`. The three required API endpoints exist and tests confirm they respond correctly.

One critical bug blocks approval: the repository's `upsert_by_provider_id` method only protects fields from None-overwrite when they are listed in the `preserve_fields` parameter, but it silently updates all other fields including those with non-None values. This means fields not explicitly listed in `PRESERVE_MATCH_FIELDS` (like `minute`, `round`, or `venue_name`) can be overwritten with None on subsequent ingestion. The ingestion code itself is correct, but the repository layer's logic violates the spec's requirement: "Never overwrite valid data with None merely because a later provider response lacks an optional field."

**Watch for:** Repository upsert logic only protects explicitly listed fields from None-overwrite; all other fields can be silently overwritten with None (**confirmed** — traced through `BaseRepository.upsert_by_provider_id`). Missing AnalysisContext enrichment for AI Analyst integration (**confirmed** — no `app/analysis/context.py` or extensions to `domain/analysis.py`). Ensemble.py provides model interfaces but no calibration or backtesting scaffolding (**confirmed** — only basic `ModelPrediction` dataclass exists).

## High-level view

The repository's upsert implementation has a gap: fields outside the `preserve_fields` list are always updated, even when the new value is None and the existing value is not. This affects optional match metadata like `venue_name`, `round`, `season`, and similar fields across all entity types. The ingestion layer correctly declares `PRESERVE_MATCH_FIELDS` and `PRESERVE_STATS_FIELDS`, but fields outside those lists remain vulnerable.

Latency tracking correctly returns None for computed metrics when authoritative timestamps are unavailable, and detects future timestamps with a 5-second grace period. Metrics are stored in a `LatencyLog` table as JSON, with indexes on entity type and creation time.

Feature engineering uses `before_datetime` throughout: the aggregator passes `match.scheduled_at` to extractors, and database queries filter on `scheduled_at < before_datetime`. xG extraction returns None when the field is absent, and the attack/defence calculator checks both `match.home_xg` and `match_statistic.xg` without fabricating values.

The database schema defines composite unique constraints on `(provider_source_id, provider_id)` for all entity types, ensuring idempotent ingestion. Timestamps are stored in UTC. Foreign keys link matches to teams, competitions, and provider sources.

The three required endpoints exist (`GET /api/v1/matches`, `GET /api/v1/matches/{id}`, `GET /api/v1/matches/{id}/prediction`) and tests confirm they return 200 for valid requests and 404 for missing entities. The response schemas are additive (new fields like `home_xg`, `data_quality` don't break existing consumers).

AnalysisContext is not implemented. No new file exists under `app/analysis/` and no enrichment was added to `domain/analysis.py`. The spec required a structured context abstraction for feeding the AI Analyst.

Ensemble scaffolding is minimal: `ensemble.py` defines a `ModelPrediction` dataclass but no calibration, backtesting, or multi-model aggregation interfaces.

## Repository None-overwrite logic has a critical gap

The `BaseRepository.upsert_by_provider_id` method implements field preservation as an opt-in mechanism:

```python
for key, value in data.items():
    existing_value = getattr(existing, key, None)
    
    # If preserve_fields specified and key is in it, check for None overwrite
    if preserve_fields and key in preserve_fields:
        if existing_value is not None and value is None:
            # Skip: don't overwrite valid data with None
            continue
    
    # Otherwise, always update
    setattr(existing, key, value)
```

The problem is the final line: `setattr(existing, key, value)` runs for every field not in `preserve_fields`, even when `value is None` and `existing_value is not None`. This violates the spec's requirement that ingestion must "never overwrite valid data with None merely because a later provider response lacks an optional field."

The ingestion layer correctly lists critical fields in `PRESERVE_MATCH_FIELDS` (home_score, away_score, home_xg, away_xg, outcome, etc.) and passes them to the repository. But fields outside that list—like `venue_name`, `season`, `round`, `minute`—are silently overwritten with None if a subsequent provider response omits them.

The test `test_ingest_match_preserves_xg_when_new_is_none` passes because `home_xg` and `away_xg` are in `PRESERVE_MATCH_FIELDS`. But there's no test for fields outside that list, and the logic would fail.

Fix: Change the upsert logic to protect all fields by default. Either:

1. Always check for None-overwrite regardless of `preserve_fields`:
   ```python
   if existing_value is not None and value is None:
       continue
   ```

2. Or require an explicit `allow_none_overwrite` parameter (defaults to False).

The current implementation is backwards: it requires callers to enumerate every field that should be protected, when the safe default is to never overwrite non-None with None.

## Latency tracking correctly handles missing timestamps

The `LatencyTracker` class initializes all timestamps to None and only calculates metrics when both operands are available:

```python
provider_to_mensione_ms = None
if self.provider_event_timestamp and self.provider_received_timestamp:
    provider_to_mensione_ms = (
        self.provider_received_timestamp - self.provider_event_timestamp
    ).total_seconds() * 1000
```

If `provider_event_timestamp` is unavailable, `provider_to_mensione_ms` remains None in the returned `LatencyMetrics`. The tracker also detects future timestamps:

```python
if provider_event_timestamp > (now + grace):
    self.has_future_timestamp = True
    self.notes = f"Provider event timestamp is in future: {provider_event_timestamp.isoformat()}"
```

When a future timestamp is detected, calculated latency metrics are set to None. The grace period is 5 seconds, which is reasonable for clock skew.

Metrics are persisted to a `LatencyLog` table with JSON storage. The repository provides `create_log` and `get_latest_for_entity` methods. The schema includes indexes on `(entity_type, entity_id)` and `created_at`.

## Feature engineering prevents data leakage

The `FeatureAggregator` passes `match.scheduled_at` as `before_datetime` to database queries, which filter on `scheduled_at < before_datetime`. The target match and all future matches are excluded. Test suite confirms this with `test_target_match_excluded` and `test_future_matches_excluded`.

## xG handling returns None when unavailable

The `AttackDefenceFeatureCalculator` checks both match record and match statistics for xG. If absent from both, `xg_per_match` is set to None. The `FeatureAggregator` logs when xG is unavailable but never fabricates values.

## Database schema enforces idempotent ingestion

All entity models define composite unique constraints on `(provider_source_id, provider_id)`. The repository's `get_by_provider_id` uses this key; if the entity exists, `upsert_by_provider_id` updates it, otherwise creates it. Different providers with the same external ID create separate records. Timestamps use `DateTime(timezone=True)` and default to UTC.

## API endpoints exist and tests pass

The three required endpoints are implemented: `GET /matches`, `GET /matches/{match_id}`, `GET /matches/{match_id}/prediction`. Tests confirm 200 responses for valid requests and 404 for missing entities. Response schemas are additive.

## AnalysisContext not implemented

The spec required an `AnalysisContext` abstraction containing match, teams, features, predictions, confidence, data quality, provider metadata, and latency. No `app/analysis/context.py` exists and no extensions were made to `domain/analysis.py`.

## Ensemble scaffolding is minimal

`ensemble.py` defines a `ModelPrediction` dataclass but no `ProbabilityCalibrator`, `BacktestRunner`, or `EnsembleAggregator` interfaces. The spec said "prepare clean interfaces" but didn't require full implementation.

## Test coverage is strong where implemented

Critical gaps: no test for None-overwrite of fields outside `PRESERVE_MATCH_FIELDS`, no test for future timestamp handling in the full ingestion flow (only unit tests), no test for AnalysisContext.
