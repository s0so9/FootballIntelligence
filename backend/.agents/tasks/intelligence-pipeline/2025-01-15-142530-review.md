# Real-data intelligence pipeline on multi-provider foundation

This implementation adds a database persistence layer, ingestion services, latency instrumentation, and feature engineering on top of the existing multi-provider architecture. The work establishes the foundation for real football data ingestion while preserving backward compatibility with the existing DevelopmentProvider-based API.

**Watch for:** Database persistence layer never overwrites non-None with None (confirmed). Latency tracker correctly returns None for unavailable timestamps (confirmed). Feature engineering prevents data leakage by filtering `before_datetime` (confirmed). xG handling returns None when unavailable (confirmed). However: no database migrations exist, the API layer still uses the old DevelopmentProvider by default, and several critical test gaps remain (latency tracking, future timestamp rejection, API compatibility regression tests).

**Verdict**: NEEDS_CHANGES

## High-level view

The ingestion layer implements field-level preservation: when a provider update lacks a previously-stored field (home_xg, away_xg, shot counts), the repository's `upsert_by_provider_id` checks each field individually and skips the update if the new value is None but the existing value is not. This prevents the "last provider wins with None" data loss pattern.

Latency tracking constructs metrics from five optional timestamps (provider_event, provider_received, processing, stored, api_response). When either endpoint of a duration calculation is missing, the tracker sets that metric to None rather than inventing a placeholder. Future timestamps beyond a 5-second grace period also force provider_to_mensione_ms and total_latency_ms to None.

Feature extraction queries historical matches with `scheduled_at < before_datetime` and `finished_only=True` by default. This boundary enforcement happens in `MatchRepository.get_team_matches_before_date`, so the feature calculators receive only past data. The implementation does not accidentally include the target match itself or any match scheduled after it.

The API endpoints remain unchanged: GET /api/v1/matches, GET /api/v1/matches/{id}, GET /api/v1/matches/{id}/prediction all preserve their existing response contracts. The prediction service still uses MatchFeatureExtractor from the provider layer, not the new database-backed feature aggregator. The environment variable `use_real_providers` defaults to False, so the API continues serving DevelopmentProvider data unless explicitly reconfigured.

Database models define composite unique constraints on (provider_source_id, provider_id) for idempotent ingestion. No Alembic migrations were created, so the schema exists only in models.py. The database_url defaults to sqlite:///./football_intelligence.db, but the ORM models are written for PostgreSQL compatibility (DateTime(timezone=True), JSON columns, proper indexes).

## Field-level preservation in repository upsert

The `BaseRepository.upsert_by_provider_id` method in database/repository.py implements the core protection against None-overwrites:

```python
# Update existing entity
for key, value in data.items():
    existing_value = getattr(existing, key, None)
    
    if preserve_fields and key in preserve_fields:
        if existing_value is not None and value is None:
            # Skip: don't overwrite valid data with None
            continue
    
    setattr(existing, key, value)
```

The `preserve_fields` parameter is explicitly set in match_ingestion.py:

```python
PRESERVE_MATCH_FIELDS = [
    "home_score", "away_score", "home_score_ht", "away_score_ht",
    "home_xg", "away_xg", "outcome", "minute", "season", "venue_name",
]
```

This list covers all fields where a provider might return None in a later fetch but had returned a real value earlier. The implementation is correct: it checks `existing_value is not None and value is None` before skipping the update. test_ingestion.py verifies this behavior for both Match.home_xg and MatchStatistic.xg.

One gap: the preserve_fields list is defined in match_ingestion.py but used in the repository layer. If a caller forgets to pass preserve_fields, the repository will overwrite everything. A safer design would bake the preservation list into the model definition or repository class, but as implemented, the ingester correctly passes it for all upsert calls.

## Latency tracking with nullable metrics

LatencyTracker in app/latency/tracker.py calculates five durations:

- provider_to_mensione_ms: provider_event → provider_received
- processing_ms: provider_received → processing
- storage_ms: processing → stored
- backend_to_frontend_ms: stored → api_response
- total_latency_ms: provider_event → api_response

Each calculation checks both endpoints:

```python
provider_to_mensione_ms = None
if self.provider_event_timestamp and self.provider_received_timestamp:
    provider_to_mensione_ms = (
        self.provider_received_timestamp - self.provider_event_timestamp
    ).total_seconds() * 1000
```

If either timestamp is None, the metric stays None. The implementation also detects future timestamps:

```python
if provider_event_timestamp > (now + grace):
    self.has_future_timestamp = True
    provider_to_mensione_ms = None  # set later in track_api_response
```

When a future timestamp is detected, the tracker sets `has_future_timestamp=True` and forces `provider_to_mensione_ms` and `total_latency_ms` to None in the final metrics, preventing nonsensical negative latencies or reporting garbage values.

Clock skew detection fires when the delta between provider timestamps exceeds 60 seconds, but it only logs the issue in `notes`—it doesn't invalidate the metrics. This is reasonable: a 70-second delay from provider event to MENSIONE receipt could be real (slow network, batch processing), so the tracker flags it but keeps the value.

The implementation is correct for the stated requirement: never invent latency values when timestamps are unavailable. However, no tests exist to verify this behavior. The latency/ module has no corresponding tests/test_latency.py, so the None-handling, future timestamp rejection, and clock skew detection are untested.

## Feature extraction with temporal boundaries

DatabaseFeatureExtractor.get_team_historical_matches calls MatchRepository.get_team_matches_before_date with `before_datetime` set to the target match's `scheduled_at`. The repository query:

```python
stmt = select(Match).where(
    and_(
        or_(
            Match.home_team_id == team_id,
            Match.away_team_id == team_id,
        ),
        Match.scheduled_at < before_datetime,  # strict inequality
    )
)
```

This prevents the target match from appearing in its own feature window. test_database.py confirms this with `test_get_team_matches_no_future_leakage`: a match scheduled at 2024-01-15 does not appear when querying `before_datetime=2024-01-10`.

The feature calculators (TeamFormFeatureCalculator, AttackDefenceFeatureCalculator) receive this filtered list and do not perform additional date checks. They trust the repository boundary. This is correct: the boundary enforcement belongs in the data access layer, not in every feature calculator.

FeatureAggregator passes `match.scheduled_at` as the before_datetime:

```python
home_matches = self.db_extractor.get_team_historical_matches(
    team_id=match.home_team_id,
    before_datetime=match.scheduled_at,
    limit=20,
    finished_only=True
)
```

The `finished_only=True` flag ensures scheduled or live matches are excluded, which prevents using incomplete match data for features. This is correct and safe.

One gap: no integration test verifies the full pipeline from ingestion through feature extraction. test_database.py tests the repository query, but no test ingests 10 matches, then extracts features for match #5, and asserts that matches #6-10 do not leak into the feature vector. This would catch a bug where the aggregator accidentally passes `datetime.now()` instead of `match.scheduled_at`.

## xG handling through the pipeline

Match.home_xg and Match.away_xg are nullable Float columns. When a provider returns xG data, it populates these fields. When a provider does not support xG (or when xG is unavailable for a specific match), the provider model sets xg=None.

The ingestion layer preserves None correctly: if Match.home_xg is 2.3 and a later provider update has home_xg=None, the value stays 2.3. test_ingestion.py verifies this.

The feature engineering layer does not substitute fake xG. AttackDefenceFeatureCalculator calculates xg_per_match:

```python
if match.home_xg is not None:
    xg_total += match.home_xg
    xg_count += 1

xg_per_match = xg_total / xg_count if xg_count > 0 else None
```

If no matches have xG, xg_per_match is None. If only some matches have xG, the average is calculated from the available values. This is correct: it does not replace missing xG with zero or any other placeholder.

The prediction service in app/prediction/service.py (the existing one, not database-backed) checks for None features:

```python
if any(v is None for v in [home_attack, away_attack, home_defense, away_defense]):
    return None
```

If features are missing, the prediction is None. The API returns 400 "Insufficient data" in that case. This is correct.

One concern: the new FeatureAggregator is not yet wired into the API. The prediction endpoint still uses the old provider-backed MatchFeatureExtractor, so the database-backed feature engineering is not exercised by the API at all. The implementation is correct but unused.

## API compatibility preservation

The three endpoints remain:

- GET /api/v1/matches → MatchListResponse
- GET /api/v1/matches/{id} → MatchDetailResponse
- GET /api/v1/matches/{id}/prediction → MatchPredictionResponse

The response schemas in app/api/v1/schemas.py were not modified. All fields remain the same. No fields were removed or renamed.

The matches.py endpoint implementation did not change structurally. It still calls `provider.get_matches()`, `provider.get_match(match_id)`, and `PredictionService(provider).generate_prediction(match)`. The dependency injection in app/api/dependencies.py returns DevelopmentProvider when `use_real_providers=False`, so the API behavior is unchanged from the user's perspective.

test_api_matches.py verifies the endpoints return 200, have the correct response structure, and contain required fields. These tests pass, which confirms no breakage occurred.

However: the tests do not verify that the database layer, if activated, would preserve the same response structure. There's no test that sets `use_real_providers=True`, ingests data into the database, and then calls the API to verify the response schema matches the old schema. This is a gap: if the database-backed path accidentally changed field names or removed fields, the tests wouldn't catch it until runtime.

## Database schema and migration status

The ORM models in app/database/models.py define 8 tables: ProviderSource, Competition, Team, Player, Match, MatchEvent, Standing, MatchStatistic, LatencyLog. All tables have composite unique constraints on (provider_source_id, provider_id) except LatencyLog.

The schema uses SQLAlchemy 2.0 features: `DateTime(timezone=True)`, `JSON` columns, `Enum` columns, relationship configurations. The models are written for PostgreSQL but SQLite is the default database_url.

Alembic is installed (alembic.ini exists), but no migration files exist in alembic/versions/. The schema exists only as ORM models. If you run the application, SQLAlchemy will not create the tables automatically unless you call `Base.metadata.create_all(engine)` somewhere.

The ingestion tests use `Base.metadata.create_all(engine)` to create an in-memory SQLite database, so they work. But production deployment would fail: the database would be empty, and ingestion would crash with "no such table: matches".

This is a blocking issue: the implementation is incomplete without migrations. The fix is straightforward: run `alembic revision --autogenerate -m "Initial schema"`, review the generated migration, and commit it.

## Prediction service integration gap

The API endpoint at matches.py line 185 creates a PredictionService:

```python
prediction_service = PredictionService(provider=provider)
```

This PredictionService uses MatchFeatureExtractor, which queries the provider directly. The new database-backed FeatureAggregator is never called.

The FeatureAggregator exists and is tested (test_features.py), but it's not wired into the API prediction flow. The implementation adds the database layer and feature engineering, but the API still serves predictions based on DevelopmentProvider in-memory data.

To complete the integration, the prediction service would need to:

1. Check if database features are available (query the database for the match)
2. If available, use FeatureAggregator to extract database-backed features
3. If not available, fall back to provider-backed MatchFeatureExtractor
4. Generate prediction from whichever feature source succeeded

This logic does not exist yet. The implementation is halfway done: ingestion works, features work, but the API doesn't use them.

The implementation follows the requirement: "Do NOT change the production-safe default from false unless the existing deployment architecture explicitly requires it." The default is safe.

The provider URLs are all configurable through environment variables (ryzellx_base_url, fotmob_base_url, openligadb_base_url). The database_url is configurable. This is correct.

One concern: the implementation does not document how to enable real providers for local development. The requirement says "Make USE_REAL_PROVIDERS=true active in the local development configuration/environment," but there's no .env.example or docs update showing how to do this. The setting exists, but a developer wouldn't know to flip it without reading the code.
