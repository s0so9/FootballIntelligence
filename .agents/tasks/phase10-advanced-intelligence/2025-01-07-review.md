## Temporal validity enforcement

All three calculators filter matches with `mws.match.scheduled_at < before_datetime` (strict less-than, not <=). This prevents matches at the prediction timestamp from leaking into historical features. The pattern appears in advanced_team_intelligence.py line 187, opponent_adjustment.py line 155, and temporal_intelligence.py line 179.

The opponent adjustment calculator has a second temporal boundary: it retrieves opponent Elo ratings via `elo_system.get_rating_at_time(opponent_id, match.scheduled_at)`, using the match timestamp rather than the prediction timestamp. This ensures opponent strength represents what was known at the time of the historical match, not current ratings. The Elo system's get_rating_at_time method (elo.py line 290) iterates through _history and returns rating_after from the last match before at_timestamp, or initial_rating if none found. The method uses `match_result.played_at >= at_timestamp` to skip future matches, which is the correct inverse of the < filter.

Test coverage includes test_cross_calculator_consistency (verifies all three agree on sample_size=5 when before_datetime excludes 2 of 7 matches), test_backtesting_scenario (walks forward through time, confirms sample size increases as data becomes available), test_elo_rating_at_time_temporal_consistency (proves rating at T stays constant even after processing later matches), and test_adjustment_uses_historical_elo_not_current (processes Elo through all matches, then calculates adjustments with cutoff excluding the last two, confirms adjusted xG differs from calculation using all matches).

## Available vs unavailable metrics

AdvancedTeamMetrics defines 20+ fields. Of these, 10 are explicitly set to None with UNAVAILABLE comments: non_penalty_xg_per_match, shots_inside_box_per_match, box_shot_percentage, big_chances_per_match, field_tilt, progressive_passes_per_match, progressive_carries_per_match, ppda, high_turnovers_per_match, set_piece_xg_per_match. These require data not present in TeamMatchStatistic: shot coordinates, xG event-type separation, progressive pass tracking, zone-based defensive actions.

The 10 available metrics extract from TeamMatchStatistic when fields are not None: xg, xg_against, shots_total, shots_on_target, possession_percentage, passes_completed, passes_attempted. Calculation logic checks `if team_stats.xg is not None` before accumulating, so missing provider data doesn't get replaced with zero.

OpponentAdjustedMetrics marks adj_box_entries as None with the comment "UNAVAILABLE until tracking" (line 61 definition, line 177 construction). Regime detection in temporal intelligence never sets detected_by='external_data' because manager tracking doesn't exist (verified by test_manager_change_unavailable and test_detected_by_field_always_statistical). The RegimeChange docstring documents this constraint.

Test test_unavailable_metrics_remain_none constructs an OpponentAdjustedMetrics and asserts adj_box_entries is None. Test test_manager_change_unavailable runs regime detection and verifies all RegimeChange.detected_by == 'statistical'.

## Elo system extension

The get_rating_at_time method (elo.py lines 290-337) extends EloRatingSystem without modifying existing behavior. It iterates through self._history (populated by process_match), checks if each EloMatchResult involves the team and occurred before at_timestamp, and returns rating_after from the last qualifying match. If no matches found, returns initial_rating.

This is a read-only query over existing state. process_match behavior unchanged, current prediction flow unaffected. The method enables opponent adjustment temporal validity without reconstructing ratings from scratch on every call—historical ratings already exist in _history, get_rating_at_time just finds the right snapshot.

Test test_elo_rating_at_time_temporal_consistency processes three matches chronologically, retrieves rating at T2 (after match 2), processes match 3, retrieves rating at T2 again, confirms both retrievals return the same value. This proves the method reconstructs consistently and doesn't use future data.

## Regime detection statistical-only

TemporalIntelligenceCalculator.detect_regime_changes (temporal_intelligence.py line 248) uses a sliding window approach: splits matches into before/after segments at each possible split point (min 5 before, min 3 after), calculates points-per-match for each segment, runs t-test, creates RegimeChange with detected_by='statistical' if p-value < 0.05. Confidence capped at 0.85 to reflect statistical inference uncertainty vs verified external events (which would be 0.95).

The RegimeChange dataclass includes detected_by field with three allowed values: 'statistical', 'external_data', 'manual'. Current implementation only produces 'statistical'. is_verified_external() returns True only for external_data/manual, which are never generated.

Manager change detection awaits schema changes: Team.manager field, manager_events table, provider integration. The detected_by field and is_verified_external method prepare for this future capability without blocking current statistical detection.

Test test_manager_change_unavailable creates 10 matches with clear performance shift (first 5 losses, next 5 wins), runs regime detection, asserts at least one regime change found, verifies all have detected_by='statistical'. Test test_detected_by_field_always_statistical runs on multiple test scenarios and confirms none produce 'external_data'.

## Cross-calculator integration

OpponentAdjustmentCalculator receives elo_system as constructor parameter, calls get_rating_at_time during calculation. Temporal and advanced team calculators operate independently.

All three export from app.features/__init__.py alongside existing calculators. MatchWithStatistics also exported. Test verification shows `from app.features import AdvancedTeamIntelligenceCalculator, OpponentAdjustmentCalculator, TemporalIntelligenceCalculator` succeeds.

Test test_cross_calculator_consistency instantiates all three with the same matches list and before_datetime, confirms sample_size=5 from all three. This proves they apply temporal filtering consistently.
