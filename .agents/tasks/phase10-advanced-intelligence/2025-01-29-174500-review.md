## Team Intelligence: AVAILABLE vs UNAVAILABLE metrics correctly separated

AdvancedTeamIntelligenceCalculator in `backend/app/features/advanced_team_intelligence.py` correctly distinguishes between metrics available from TeamMatchStatistic and those requiring future provider integration. The dataclass AdvancedTeamMetrics declares 11 UNAVAILABLE metrics explicitly in comments: `non_penalty_xg_per_match`, `shots_inside_box_per_match`, `box_shot_percentage`, `big_chances_per_match`, `field_tilt`, `progressive_passes_per_match`, `progressive_carries_per_match`, `ppda`, `high_turnovers_per_match`, `set_piece_xg_per_match`. All 11 are initialized to None by default and set to None in the return statement (lines 222-235).

AVAILABLE metrics extracted from TeamMatchStatistic: `xg` → `xg_for_per_match`, `xg_against` → `xg_against_per_match`, `shots_total` → `shots_per_match`, `shots_on_target` → `shots_on_target_per_match`, `possession_percentage` → `possession_avg`. The calculator checks `if team_stats.xg is not None` before accumulating, preventing silent None → 0 conversion. Derived metric `xg_per_shot` calculated only when both xg and shots_total exist. Home/away venue splits calculated separately via `home_xg_for_per_match` and `away_xg_for_per_match`.

Data quality score weighted by metric completeness: 30% xG coverage + 30% shots coverage + 20% possession coverage + 20% sample size adequacy. Provenance tracks `matches_with_xg`, `matches_with_shots`, `matches_with_possession` separately. The calculator returns metrics even when some fields are None, allowing partial feature extraction when only xG or only shots are available.

## Temporal validity: strict < comparison enforced across all calculators

All three calculators filter matches with `if mws.match.scheduled_at < before_datetime`, not `<=`. This appears identically in:
- `advanced_team_intelligence.py` line 187
- `opponent_adjustment.py` line 155  
- `temporal_intelligence.py` line 179

The comment `# STRICT < to prevent leakage` documents the rationale. Test `test_strict_less_than_comparison` in `test_temporal_leakage.py` verifies a match exactly at cutoff_date is excluded, expecting sample_size=2 from 4 matches where one lands exactly on the cutoff. All three calculators pass this test.

Walk-forward backtesting test `test_backtesting_scenario` makes predictions at three historical timestamps and verifies sample sizes increase monotonically (2, 3, 4) as the cutoff advances, confirming each prediction sees only data available at that timestamp. Cross-calculator consistency test `test_cross_calculator_consistency` verifies all three calculators agree on sample_size=5 when given 7 matches with cutoff after match 5.

## Opponent adjustment uses historical Elo at match time

OpponentAdjustmentCalculator retrieves opponent strength via `self.elo_system.get_rating_at_time(opponent_id, mws.match.scheduled_at)` at line 235. This new method in EloRatingSystem (elo.py lines 290-337) reconstructs historical ratings by iterating through `self._history` to find the last match involving the team before `at_timestamp`, returning `rating_after` from that match or `initial_rating` if no matches found.

The implementation uses `if match_result.played_at >= at_timestamp: continue` to skip future matches, maintaining temporal validity. Test `test_elo_rating_at_time_temporal_consistency` in test_temporal_leakage.py processes two matches, retrieves team_b's rating after match 1, processes match 2, then retrieves team_b's rating after match 1 again. The two retrievals must return identical values, proving get_rating_at_time() provides truly historical ratings unaffected by subsequently processed matches.

Test `test_adjustment_uses_historical_elo_not_current` in test_opponent_adjustment.py processes 6 matches that change opponent ratings, then calculates opponent-adjusted metrics using only the first 3 matches via before_datetime cutoff. The test verifies adjustment uses opponent ratings as they were during matches 1-3, not their ratings after matches 4-6. Opponent adjustment formula: `adjusted_xg = raw_xg * (league_avg_elo / opponent_elo)`. Stronger opponents (higher Elo) reduce adjusted performance; weaker opponents increase it. League average simplified to `initial_rating` (1500) since Elo is zero-sum.

## Regime detection: statistical only, no external manager data

TemporalIntelligenceCalculator.detect_regime_changes() uses sliding window with t-test to detect significant performance shifts. The method compares points-per-match distributions in before/after periods using `stats.ttest_ind()` from scipy. Significance threshold 0.05, minimum 5 matches before and 3 matches after the changepoint. When significant shift detected, creates RegimeChange with `detected_by="statistical"` (line 324) and `event_type="statistical_shift"`.

Comments document manager change UNAVAILABLE: "No manager tracking in Team model", "No manager_events table", "detected_by always 'statistical' in current implementation". RegimeChange dataclass defines `detected_by: str` field with options "statistical", "external_data" (future), "manual" (future). Method `is_verified_external()` returns True only when detected_by in ["external_data", "manual"], which is never true in current implementation.

Statistical regime changes capped at confidence 0.85 via `min(confidence, 0.85)` at line 326, reflecting lower confidence than verified external events (which would be 0.95). Test `test_manager_change_unavailable` verifies detected_by is never "external_data". Test `test_detected_by_field_always_statistical` verifies all detected regime changes have detected_by="statistical".

## Exponential recency weighting correctly implemented

TemporalIntelligenceCalculator applies exponential decay with configurable decay_factor (default 0.95). Most recent match (last in chronologically-ordered list) receives weight 1.0. Previous match receives weight `decay_factor^1 = 0.95`. Match before that receives `decay_factor^2 = 0.9025`, etc. Implementation at lines 360-373 calculates weights from most recent backwards: `matches_back = num_matches - 1 - i` and `weight = self.weighting.decay_factor ** matches_back`.

Weighted form calculated as `sum(points * weight) / sum(weight)`. Weighted xG calculated as `sum(xg * weight) / sum(weight)` where xg exists. Test `test_exponential_weighting_calculation` constructs 5 matches with alternating win/loss pattern, calculates expected weighted average manually, and verifies calculator produces matching result within 0.01 tolerance.

TemporalWeighting dataclass supports alternative halflife_matches parameterization, converting to decay_factor via `0.5 ** (1.0 / halflife_matches)` in __post_init__. Form trend detection uses linear regression over match points, classifying slope >0.1 as "improving", <-0.1 as "declining", else "stable". Form acceleration returns the slope directly (points per match per match).

## Post-regime form calculation requires minimum sample

After detecting regime change, TemporalIntelligenceCalculator calculates post_regime_form by filtering matches to those on or after regime_change_date, then averaging points. Requires minimum 3 post-regime matches (line 437), returning None if insufficient. This prevents unstable post-regime metrics when only 1-2 matches exist after the change.

Test `test_post_regime_form_calculation` creates 10 matches with poor form in first 5 and good form in last 5, triggers regime detection, verifies post_regime_form reflects the improved period. Test `test_regime_detection_temporal_validity` creates 8 matches with poor form in first 5 and good form in last 3, applies cutoff after match 5, verifies regime detection does not see the future good form (form_trend must be "declining" or "stable", not "improving").

## Data quality scoring reflects metric completeness

AdvancedTeamMetrics.data_quality_score calculated as weighted combination: 30% xG coverage + 30% shots coverage + 20% possession coverage + 20% sample size adequacy. xG coverage = matches_with_xg / sample_size. Sample size adequacy = 1.0 if sample_size >= min_matches, else sample_size / min_matches.

OpponentAdjustedMetrics.data_quality_score calculated as: 60% opponent rating coverage + 40% adjusted metric completeness. Opponent rating coverage = matches_with_opponent_rating / sample_size. Metric completeness = (available_adj_metrics / 2), counting adj_xg_for and adj_shots.

TemporalIntelligenceMetrics does not have data_quality_score field, relying on sample_size and form_trend=None when insufficient data. This asymmetry is acceptable since temporal weighting is less sensitive to missing individual match data (exponential decay naturally handles gaps).

## Home/away venue context preserved

AdvancedTeamMetrics includes `home_xg_for_per_match` and `away_xg_for_per_match` fields (lines 91-92), calculated separately via venue filtering in _calculate_advanced_from_matches(). Requires minimum 3 home matches and 3 away matches for venue splits. When insufficient, venue-specific fields remain None.

OpponentAdjustedMetrics includes `home_away_context: str = "all"` field (line 74), documenting whether adjustment is home-only, away-only, or combined. Current implementation uses "all" (combined), but field is ready for future venue-specific adjustment.

TemporalIntelligenceMetrics does not have venue separation, which is correct since recency weighting and regime detection should operate on full match sequence regardless of venue. Splitting by venue would fragment temporal patterns.

## Insufficient data handling returns metrics with None values

All three calculators check sample size against min_matches (default 5 for advanced, 3 for temporal) and return metrics structure with populated sample_size but None for calculated fields when insufficient. This allows callers to distinguish "not enough data" from "data exists but metric unavailable".

AdvancedTeamIntelligenceCalculator returns AdvancedTeamMetrics with sample_size=len(finished_matches) and all metric fields None when sample_size < min_matches (lines 195-202). OpponentAdjustmentCalculator returns OpponentAdjustedMetrics with adjustment_method="insufficient_data" when sample_size < min_matches (lines 160-166). TemporalIntelligenceCalculator returns TemporalIntelligenceMetrics with None for all temporal fields when sample_size < min_matches (lines 184-190).

Test `test_insufficient_matches` in each test file verifies this behavior. This design enables predictors to log "insufficient historical data" rather than failing or using unstable metrics from 1-2 matches.
