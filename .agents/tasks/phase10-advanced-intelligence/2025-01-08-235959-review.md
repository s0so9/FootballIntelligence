# Common Opponent Intelligence Implementation

A new contextual intelligence feature that compares team performance against shared opponents. The implementation discovers common opponents dynamically from historical matches, compares performance metrics with recency weighting, and calculates explicit statistical confidence. Direct H2H matches are excluded from common opponent analysis, preserving their independence.

**Watch for:** None remaining — all data integrity, temporal validity, and architectural concerns have been addressed in the implementation.

**Verdict**: APPROVED

## High-level view

The implementation discovers common opponents by computing set intersections of historical opponents for both teams, excluding direct H2H matches and enforcing strict temporal cutoffs. Performance comparison uses weighted averages across multiple metrics (points, xG, xGA, shots), with exponential decay for recency and explicit tracking of home/away context matching. Confidence calculation follows a three-factor formula (sample × recency × context), and signal strength determination uses conservative thresholds that prevent naive transitive conclusions. When fewer than three common opponents exist, the system returns None for all comparison fields rather than attempting low-confidence claims. The calculator reuses MatchWithStatistics from existing Group 1 infrastructure and applies the same exponential decay pattern used in temporal intelligence. Missing metrics remain None throughout the pipeline, never fabricated. The feature integrates into MatchFeatureSnapshot as an optional field and exports through the features module.

## Discovery and temporal validity

Common opponent discovery operates on set intersection: home team's opponents ∩ away team's opponents, with direct H2H matches explicitly filtered out. The temporal cutoff uses strict `<` comparison (`match.scheduled_at < before_datetime`), never `<=`. Only finished matches count. Tests verify boundary conditions: a match scheduled exactly at the prediction timestamp is excluded, future matches never leak in.

The discovery logic walks both teams' historical matches, identifies opponents (the other team in each match), excludes matches where the opponent is the fixture's opposing team, and computes the intersection. This is correct and matches the spec's requirement that common opponent intelligence is independent of direct H2H.

Three temporal validity tests cover: matches before the cutoff included, matches at the cutoff excluded (strict `<`), and future matches excluded. All pass.

## H2H separation

Direct H2H matches are excluded in `_discover_common_opponents` with explicit checks: `if opponent_id == away_team_id: continue` for home team matches, and `if opponent_id == home_team_id: continue` for away team matches. Test `test_exclude_direct_h2h_from_common_opponents` confirms that when both teams have played each other and also played Team X, only Team X appears as a common opponent. The H2H matches themselves are not counted. This preserves the independence of direct H2H and common opponent analysis as required.

## Performance comparison and missing data

For each common opponent, the calculator extracts `CommonOpponentMatch` records containing result, goals, points, and optional advanced metrics (xG, xGA, shots, shots on target, possession). The extraction logic pulls from `MatchWithStatistics.get_team_statistics()`. If a statistic is absent, the field remains None. The `has_advanced_stats` flag is set only when xG or shots exist.

Weighted averages are calculated separately for each metric. Points are always available (derived from the match result). xG differentials are calculated only when both teams have xG data for their matches against the common opponent. Missing xG results in `xg_differential = None`, not zero. Test `test_xg_comparison_none_when_unavailable` verifies that matches without xG still produce points comparison but leave xG fields as None. Test `test_missing_xg_handled_gracefully` confirms the same at the aggregated level.

Shots follow the same pattern: calculated when available, None when missing. No fabrication occurs at any level.

## Recency weighting

Recency weight calculation uses exponential decay: `weight = decay_factor ^ (days_since_match / 30)`. The default decay factor is 0.95, matching the temporal intelligence pattern. Days are normalized by 30 to create monthly periods. The weight is clamped to [0, 1].

Weights are calculated per match and applied when computing weighted averages for points, xG, xGA. Test `test_exponential_decay_applied` confirms that a match 5 days ago receives higher weight than a match 60 days ago. Test `test_recency_factor_in_confidence` confirms that recent matches yield higher confidence than old matches when all other factors are equal.

The recency weighting integrates into the confidence calculation as `recency_factor`, computed as the average recency weight across all matches against common opponents.

## Context normalization

Context match rate measures the proportion of comparisons that match venue: home vs home or away vs away. The calculator preserves `is_home` in each `CommonOpponentMatch`. When computing context match rate for one common opponent, it counts how many home team matches were at home and how many away team matches were away, sums them, and divides by total matches.

Test `test_home_away_context_normalization` verifies: when home team played home vs Team X and away team played away vs Team X, context match rate is 1.0 (both matches align with the fixture's venue). When home team played away vs Team X and away team played home vs Team X, context match rate would be 0.0 (neither aligns).

The context factor feeds into the confidence formula as the average context match rate across all common opponents.

## Confidence calculation

The confidence formula is explicit:

```
confidence = sample_factor × recency_factor × context_factor
```

where:
- `sample_factor = min(1.0, n_common_opponents / 5.0)` — penalizes small samples
- `recency_factor` — average recency weight across all matches
- `context_factor` — average context match rate across all opponents

Test `test_confidence_formula_three_factors` verifies that 3 common opponents with recent matches and perfect context matching yields moderate confidence (sample factor 0.6, recency ~0.9+, context 1.0). Test `test_confidence_with_many_common_opponents` verifies that 5+ common opponents yield sample_factor = 1.0. Test `test_confidence_with_few_common_opponents` verifies that fewer than `min_common_opponents` (default 3) results in `comparison_confidence = 0.0` and all comparison fields set to None.

The insufficient-data threshold is enforced in `calculate_common_opponent_intelligence`: when `len(common_opponent_ids) < self.min_common_opponents`, the aggregation step is skipped entirely, leaving all comparison fields as None. This prevents low-confidence claims based on one or two shared opponents.

## Signal strength determination

Signal strength is determined by:

```python
if differential is None:
    return "neutral"
if abs(differential) < min_differential_threshold:  # 0.3
    return "neutral"
if confidence < min_confidence_threshold:  # 0.5
    return "neutral"
if differential > 0.5 and confidence > 0.7:
    return "home_favored"
elif differential < -0.5 and confidence > 0.7:
    return "away_favored"
else:
    return "neutral"
```

Three barriers to a non-neutral signal: differential must be present, differential must be meaningful (|d| ≥ 0.3), and confidence must exceed 0.5. For a "home_favored" or "away_favored" signal, both the differential and confidence must be high (d > 0.5 or d < -0.5, and confidence > 0.7).

Test `test_signal_neutral_when_small_differential` verifies that similar performance (differential near zero) yields neutral. Test `test_signal_neutral_when_low_confidence` verifies that even with a large differential, low confidence (one common opponent) yields neutral. Test `test_no_naive_transitive_logic` explicitly tests the transitive fallacy: home beat X, away lost to X, but only one common opponent → signal is neutral, not home_favored.

Tests `test_signal_home_favored_with_evidence` and `test_signal_away_favored_with_evidence` confirm that only with 5 common opponents, consistent performance differences, and high confidence do directional signals emerge.

## Data quality score

The data quality score combines sample size (0.0-0.5) and metric availability (0.0-0.5):

- 5+ common opponents: +0.5
- 3-4 common opponents: +0.3
- 1-2 common opponents: +0.1
- Available metrics: (count of non-None differentials / 4) × 0.5

Test `test_data_quality_score_calculated` confirms that 5 opponents with all metrics yields `data_quality_score ≥ 0.8`, while 1 opponent with only basic metrics yields `data_quality_score < 0.5`.

## Architecture reuse

The implementation imports `MatchWithStatistics` from `advanced_team_intelligence` and uses its `get_team_statistics()` method. It does not duplicate the data structure or query logic. Exponential decay uses the same formula as `temporal_intelligence.py` (decay factor raised to power of normalized days).

The `CommonOpponentIntelligence` dataclass is added to `MatchFeatureSnapshot` as an optional field (`common_opponent_intel: Optional[CommonOpponentIntelligence] = None`). Exports are added to `features/__init__.py`. The integration is minimal and follows the existing pattern of optional intelligence fields.

No new historical data access layer is created. The calculator accepts lists of `MatchWithStatistics`, which the caller (feature aggregator or prediction pipeline) must fetch using existing repository methods.
