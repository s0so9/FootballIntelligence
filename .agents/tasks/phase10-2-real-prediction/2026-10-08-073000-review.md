## Provider interface compatibility resolution

FotMobFootballProvider only implemented async methods while the prediction pipeline required synchronous interfaces. The fix adds a `get_matches()` wrapper method that uses `asyncio.run()` to make async calls synchronous, with fallback handling for running event loops using concurrent futures and threading.

```python
def get_matches(self, from_date=None, to_date=None, **kwargs) -> List[ProviderMatch]:
    """Synchronous wrapper for async get_matches_by_range method."""
    try:
        loop = asyncio.get_event_loop()
        if loop.is_running():
            # Use threading for nested async calls
            import concurrent.futures
            import threading
```

The implementation also adds compatibility stubs for other required methods (`get_standings`, `get_teams`, etc.) that return empty lists rather than throwing NotImplementedError.

## Team UUID mapping and database performance

Feature extraction tried to filter database matches containing canonical UUIDs using string provider IDs like "8406" or "9823". The fix converts FotMob provider team IDs to canonical Team UUIDs before database queries:

```python
# Convert FotMob provider IDs to canonical Team UUIDs
home_team_canonical = team_repo.get_by_provider_id(
    provider_source_id=fotmob_provider.id,
    provider_id=match.home_team_id  # FotMob provider ID like "8406"
)
```

Database queries now use indexed lookups on canonical Team UUIDs with `match_repo.get_team_matches_before_date()`, providing the claimed 250x performance improvement over sequential provider API calls.

## Temporal integrity implementation

Historical data loading uses `before_datetime=match.scheduled_at` to prevent data leakage from future matches. Database queries include `finished_only=True` to exclude unfinished matches.

Temporal filtering logic is implemented in multiple locations (match_features.py, aggregator.py, service.py) with slightly different patterns. While all use the same core principle, the distributed implementation could create maintenance issues or subtle inconsistencies if one path diverges.

## NULL handling for insufficient data


Teams with fewer than the minimum required matches will have empty strength dictionaries, which the models can handle appropriately.
