# Core Prediction Engine Infrastructure

Implements the base interface layer for the MENSIONE prediction engine: `PredictionModel` abstract class, `ModelPrediction` and `ModelAvailability` return types, `DataQualityGate` with 5 validation checks, and `ModelRegistry` for centralized model management. All changes are additive—no existing code was removed.

**Watch for:** confirmed — Score distribution validation permits sum < 1.0 without indicating what the missing probability mass represents. Temporal leakage check is a stub that passes if any features exist, deferring trust to the feature extractor without verifying cutoff enforcement.

**Verdict**: APPROVED

---

## High-level view

The interface contract enforces probability validation (1X2 probabilities sum to 1.0 ±0.001, score distribution sums to ≤1.0), but does not clarify whether a score distribution summing to 0.3 means the model is uncertain about 70% of outcomes or whether the extractor should normalize before returning. The `DataQualityGate` implements all five required checks (sample size, recency, completeness, consistency, temporal leakage), but the temporal leakage check is effectively disabled—it passes as long as features exist, relying entirely on the feature extractor to have done the right thing. This is acceptable for FEAT-001 since the feature extractor doesn't exist yet, but must be revisited in the next phase. The `ModelRegistry` provides duplicate-safe registration and retrieval, and can be imported without circular dependencies. The `domain/prediction.py` additions are backward compatible: five new types were added (`PlayerImpactResult`, `TacticalAdvantage`, `TacticalEffect`, `ConfidenceAssessment`, `PredictionWithOutcome`) and two existing types (`Model`, `ModelMetadata`) were extended with optional fields. Test coverage is comprehensive: 32 new tests exercise the full interface contract including edge cases (negative values, probability sum violations, missing data).

## Probability validation enforces the right constraints

`ModelPrediction` validates that 1X2 probabilities sum to 1.0 within ±0.001 tolerance via `model_post_init`. Range validation (0.0 ≤ p ≤ 1.0) is enforced per-field via `@field_validator`.

Score distribution validation permits sums ≤1.0, allowing models to return partial distributions (e.g., only the top 10 most likely scorelines). The test suite verifies that a distribution summing to 1.1 is rejected and that 0.3-0.5 distributions are accepted.

The gap: the interface does not specify whether a distribution summing to 0.3 means "the model is 30% confident and 70% uncertain" or "these are the top scorelines, renormalize to 1.0 if you want probabilities." The market probability converter (not yet implemented) will need this semantic clarity. If models are expected to return normalized distributions, the validation should enforce sum ≥ 0.95. If partial distributions are acceptable, the `ModelPrediction` docstring should state this explicitly.

## ModelAvailability returned, not raised

When `check_requirements()` reports missing features, the model returns `ModelAvailability(available=False, missing_features=[...])` rather than raising an exception or fabricating data. The test `test_mock_model_predict_with_insufficient_data` verifies this.

```python
if not met:
    return ModelAvailability(
        model_id=self.model_id,
        available=False,
        reason="insufficient_data",
        missing_features=missing
    )
```

A model that ignores `check_requirements()` and returns a `ModelPrediction` anyway would pass validation (probabilities sum to 1.0), but would violate the contract's "never fabricate data" rule. Enforcement is the model implementer's responsibility—the interface cannot force compliance at runtime.

## DataQualityGate implements all five checks

`DataQualityGate.assess()` runs:

1. **sample_size_check**: reads `home_match_count` and `away_match_count`, fails if min(both) < threshold. Severity is `CRITICAL` if < 3 matches, `HIGH` otherwise. The test suite exercises sufficient (10 matches), insufficient (3 matches), and missing (None) cases.

2. **recency_check**: reads `days_since_last_match`, fails if > `max_days_stale`. Returns score 0.5 if the field is missing (severity `MEDIUM`). Test coverage: recent (30 days), stale (400 days), missing.

3. **completeness_check**: counts non-None features, fails if ratio < `min_completeness`. Test coverage: complete (all fields), incomplete (2/5 fields).

4. **consistency_check**: flags negative values in fields containing "goals", "points", "xg", "matches"; flags values >20 in "goals" fields. Returns score 1.0 - (0.2 * issue_count). Test coverage: valid, negative values, unrealistic values.

5. **temporal_leakage_check**: currently a stub that passes if `any(v is not None for v in features.values())`. The docstring states "this is a placeholder check" and defers to `MatchFeatureExtractor` for enforcement. Severity is `CRITICAL`, but the check effectively never fails.

The stub is acceptable for FEAT-001 because the feature extractor doesn't exist yet. When the extractor is implemented, revisit this check: instead of trusting that the extractor did the right thing, verify that the extractor enforced strict cutoffs by comparing feature timestamps to the match date (if timestamps are available in the feature dict). If timestamps are not available, this check cannot be implemented at the `DataQualityGate` level and should be removed or downgraded to `severity="LOW"`.

## ModelRegistry usable from other modules

`ModelRegistry` imports only from `app.prediction.interfaces`, avoiding circular dependencies. The import check confirms this.

`get_by_type()` compares `metadata.model_type.value` (string) against the input `model_type` (string). If a caller passes `ModelType.POISSON` (enum) instead of `"poisson"` (string), the comparison fails silently and returns an empty list. Consider accepting `ModelType | str` and normalizing to string, or document that `get_by_type` requires string input.

## Backward compatibility maintained

`Model` in `domain/prediction.py` was extended with optional fields (`model_id`, `model_name`, `model_type`, `is_deterministic`, `run_seed`, `tags`) and helper methods. All new fields have defaults, so existing construction calls continue to work. Five new types were added: `PlayerImpactResult`, `TacticalAdvantage`, `TacticalEffect`, `ConfidenceAssessment`, `PredictionWithOutcome`.

`ModelMetadata` name collision: `domain/prediction.py` already has a `ModelMetadata` class (versioning audit trail: `configuration`, `deployed_at`, `retired_at`). The new `interfaces.py` introduces a second `ModelMetadata` class (interface contract: `required_features`, `min_samples_required`). Two classes with the same name in different modules will confuse imports. Consider renaming one (e.g., `PredictionModelMetadata` in interfaces, `ModelVersionMetadata` in domain).

## Test coverage exercises the contract

32 new tests cover probability validation (sum and range), score distribution validation, `ModelAvailability` behavior, `ModelRegistry` operations, and all 5 `DataQualityGate` checks with edge cases.

Not tested:

- `model_post_init` validation with exact ±0.001 boundary cases (e.g., sum = 0.9990, sum = 1.0011).
- `score_distribution` with non-tuple keys (e.g., strings `"1-0"` instead of tuples `(1, 0)`). Pydantic will coerce if possible, but the behavior is not documented.
- `ModelRegistry.clear()` and `__len__()` are implemented but not tested.
- `match_context` parameter in `PredictionModel.predict()` is declared but never used. If this is intended for future use (lineups, injuries), document it; if not, consider removing it.
