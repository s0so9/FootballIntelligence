# FEAT-003 Specialized Models Implementation

**Verdict**: CHANGES_REQUESTED

**Watch for:** Missing ModelType enum value causes import errors (confirmed), test assertion mismatches reveal incomplete error propagation (likely), form calculator returns None when tests expect scores due to threshold logic (confirmed), 9 test failures block integration into ensemble.

## Summary

FEAT-003 implements three new specialized prediction models for the MENSIONE Prediction Engine: FormAdjustedModel (time-decayed form weighting), MonteCarloSimulation (market probability derivation through simulation), and LogisticRegressionModel (PredictionModel interface). The implementation correctly follows the PredictionModel interface contract, handles unavailable data through ModelAvailability, and maintains backward compatibility. The Monte Carlo simulator derives comprehensive market probabilities (1X2, O/U, BTTS, team totals) from Poisson-based simulation. The form adjustment algorithm applies opponent-adjusted time-weighted scoring to base model lambdas. However, 9 of 37 tests fail due to: missing ModelType.FORM_ADJUSTED enum value (1 failure, import-blocking), incomplete error propagation in availability reasons (3 failures), and form calculator threshold logic that returns None when tests expect scores (4 failures). These failures prevent safe integration into the ensemble engine.

## High-level view

The three models implement the PredictionModel interface with proper ModelAvailability handling instead of exceptions. FormAdjustedModel wraps any base model and adjusts its expected goals using time-decayed opponent-weighted form scores in [-1, 1] range through the formula `lambda_adjusted = lambda_base * (1 + form_weight * form_score)`. MonteCarloSimulation runs configurable simulations (default 10,000) to derive market probabilities from scoreline frequency, including all markets required by the design (1X2, correct score top-25, O/U at four lines, BTTS, team totals at three thresholds). LogisticRegressionModel receives the PredictionModel interface while preserving its original training API through a renamed `predict_legacy` method. OpponentAdjustedFormCalculator computes form scores using exponential time decay and strength-of-schedule weighting from either Elo ratings or goal ratios.

The missing FORM_ADJUSTED enum value blocks imports and prevents model instantiation. Error propagation from base models to wrapper models loses specificity: FormAdjustedModel and MonteCarloSimulation return generic "insufficient_data" instead of preserving the base model's unavailability reason like "base_model_unavailable: insufficient_data". The form calculator applies a 5-match minimum threshold after time-decay filtering, causing it to return None when recent match sets drop below the threshold even when total historical matches exceed it.

## ModelType enum gap blocks instantiation

FormAdjustedModel.get_metadata() returns `model_type=ModelType.FORM_ADJUSTED`, but this enum value doesn't exist in `backend/app/domain/enums.py`. The enum defines POISSON, DIXON_COLES, ELO, NEGATIVE_BINOMIAL, MONTE_CARLO, LOGISTIC_REGRESSION, but no FORM_ADJUSTED. Without it, any code that imports or instantiates FormAdjustedModel will fail at the enum attribute access. The test file `test_form_adjusted.py` includes a test `test_metadata_includes_base_model_requirements` that explicitly checks `metadata.model_type == ModelType.FORM_ADJUSTED`, and this test is marked as one of the 9 failures in the verification report. Add `FORM_ADJUSTED = "form_adjusted"` to the ModelType enum.

## Form adjustment lambda formula and distribution recalculation

FormAdjustedModel wraps a base model, extracts home/away form scores from features, calculates multipliers `1.0 + (form_weight * form_score)`, applies them to base lambdas, enforces minimum lambda of 0.1, then regenerates the score distribution using a simple Poisson `_calculate_poisson_distribution` method. The distribution is normalized. 1X2 probabilities are summed from the distribution and normalized again. The adjustment formula matches the design specification. The minimum lambda enforcement prevents negative or zero expected goals when extreme negative form combines with low base rates. Confidence is adjusted by `base_confidence * (1.0 - abs(home_form - away_form) * 0.1)` to reduce confidence when form differences are extreme.

Metadata preserves the base model's feature requirements and adds `home_form_score`, `away_form_score`, `home_form_matches_used`, `away_form_matches_used`. The wrapper returns ModelAvailability when the base model returns ModelAvailability, when form scores are None, or when form_matches_used < min_matches_for_form. When form scores are unavailable but base prediction succeeds, the wrapper returns the base prediction unchanged with a metadata flag `form_adjustment_applied: False` and slightly reduced confidence (0.9x).

## Monte Carlo market derivation completeness

MonteCarloSimulation runs n_simulations iterations (default 10,000), each drawing home_goals and away_goals from Poisson distributions using `_poisson_sample`. For large lambdas (>30), it uses normal approximation N(lambda, sqrt(lambda)) instead of Knuth's algorithm to avoid numerical issues. The simulation accumulates scoreline counts, 1X2 counts, over/under counts at lines [0.5, 1.5, 2.5, 3.5], BTTS yes/no counts, and team-specific totals at lines [0.5, 1.5, 2.5].

All market probabilities are derived by dividing counts by n_simulations. The score distribution is pruned to the top 25 scorelines by probability. Over/under probabilities represent P(total_goals > line). Team totals represent P(team_goals > line). BTTS yes requires both teams scored > 0. All these markets are stored in the metadata dict, not in dedicated PredictionModel fields, because the interface defines only home_win_prob, draw_prob, away_win_prob as first-class fields.

Confidence is calculated as `sim_confidence * outcome_confidence` where sim_confidence = min(1.0, n_simulations / 10000) and outcome_confidence = 0.7 + (uniform_distance * 0.3). Uniform distance measures how far the 1X2 distribution is from (0.333, 0.333, 0.333).

The model can operate in two modes: wrap a base model to get lambdas, or consume lambdas directly from features (home_expected_goals, away_expected_goals). When wrapping a base model and the base returns ModelAvailability, Monte Carlo propagates that unavailability with reason "base_model_unavailable: {base_prediction.reason}". When operating without a base model and expected_goals features are missing, it returns ModelAvailability with reason "expected_goals_unavailable". However, the check_requirements method doesn't distinguish these cases correctly: it returns generic missing feature names instead of the specific reason strings that appear in the predict method. Tests expect to find "base_model_unavailable" or "expected_goals_unavailable" as substrings in the reason field, but the actual implementation returns "insufficient_data" from the check_requirements path.

## Logistic regression interface integration preserves backward compatibility

LogisticRegressionModel originally had a predict method that returned LogisticRegressionPrediction. The refactor adds a new predict method conforming to PredictionModel interface (returns ModelPrediction | ModelAvailability) and renames the original to predict_legacy. The new predict method checks is_fitted and feature completeness (>= 50%), returns ModelAvailability if either fails, otherwise calls predict_legacy internally and maps the LogisticRegressionPrediction fields to ModelPrediction.

Expected goals are approximated from 1X2 probabilities using heuristics: `home_expected = 1.0 + (home_win_prob * 0.8) - (away_win_prob * 0.4)`. This is a rough inverse mapping since logistic regression directly predicts 1X2 without modeling scorelines. Confidence is derived from prediction certainty: `0.5 + (max_prob - 0.333) * 0.75` maps the range [0.333, 1.0] (uniform to certain) to [0.5, 1.0]. Data quality is feature availability ratio.

The fit() method, training interface, and LogisticRegressionPrediction dataclass remain unchanged. Existing code that trains the model and calls predict_legacy continues to work.

## Opponent-adjusted form calculation with time decay and strength weighting

OpponentAdjustedFormCalculator.calculate receives home_matches and away_matches lists, filters each by reference_date (only past matches), then calls `_calculate_team_form` for each team. The team-level calculation checks if past_matches < min_matches (default 5) and returns None if insufficient. Otherwise it takes the most recent 20 matches, iterates through them, and computes a weighted score.

For each match, it calculates:
- time_weight = exp(-time_decay_rate * days_ago / 30) using exponential decay per 30-day period
- match_points = 3.0 for win, 1.0 for draw, 0.0 for loss from the team's perspective
- opponent_strength = estimated from Elo (if provided) or from opponent's recent goal ratio
- strength_multiplier = 0.5 + (opponent_strength * 0.5) maps strength to [0.5, 1.5]
- total_weight = time_weight * strength_multiplier
- weighted_sum += match_points * total_weight

Average weighted points = weighted_sum / weight_sum. This is mapped to [-1, 1] by `(avg_weighted_points - 1.5) / 1.5` since 0 points = -1, 1.5 points = 0, 3 points = +1. The score is clamped to [-1, 1].

The min_matches threshold creates a cliff: tests provide exactly 5-6 matches expecting valid scores, but if the chronological filter or processing reduces the effective count below 5, the calculator returns None. The threshold exists for statistical validity but tests written for the boundary case hit this cliff.

The strength estimation fallback (when Elo unavailable) uses the opponent's goal ratio from their recent 10 matches. If the opponent has < 3 matches in the dataset, it defaults to 1.0 (average strength). The goal ratio is goals_scored / goals_conceded, mapped to strength [0.5, 1.5] with ratio < 0.75 = weak, 0.75-1.25 = average, > 1.25 = strong.

## Error propagation through model wrappers incomplete

FormAdjustedModel checks base model requirements and form requirements separately in check_requirements. If base requirements fail, it adds base_missing to the missing list. If form requirements fail, it adds form-specific items. The method returns (len(missing) == 0, missing). In the predict method, if check_requirements returns False, it creates ModelAvailability with reason "insufficient_data". The specific reason "base_model_unavailable" only appears in a separate code path where base_model.predict() is called and returns ModelAvailability. But check_requirements doesn't distinguish "base unavailable" from "form unavailable", so when check_requirements fails due to base requirements, the reason is generic.

Tests expect the reason field to contain "base_model_unavailable" as a substring. The test `test_model_unavailable_when_base_unavailable` provides features with form scores but missing Poisson requirements. The test expects `"base_model_unavailable" in result.reason`. But the actual code path goes through check_requirements → missing includes base features → reason = "insufficient_data". The substring check fails.

MonteCarloSimulation has the same pattern. When base_model.predict() returns ModelAvailability, the reason is set to f"base_model_unavailable: {base_prediction.reason}". But when check_requirements fails due to base model unavailability, the reason is generic. The test `test_unavailable_when_base_model_unavailable` expects the substring "base_model_unavailable" but gets "insufficient_data".

Fix: check_requirements should call base_model.check_requirements separately and construct a reason string that distinguishes base model issues from wrapper-specific issues. Or, remove the early check_requirements gate and rely entirely on base_model.predict() propagation, then check form-specific requirements only.

The failures indicate edge cases where error messages don't match test expectations (reason string content) or where threshold logic is stricter than tests anticipated (min_matches after filtering).
