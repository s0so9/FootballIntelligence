## High-level view

The market derivation engine is mathematically sound. It sums scoreline probabilities to derive 1X2, double-chance, over/under, BTTS, team totals, exact score top-N, and Asian handicaps, with validation that complementary markets sum to 1.0. The score distribution drives everything; no probabilities are fabricated.

The MENSIONE pick generator ranks markets by conviction (distance from 50%) when odds are unavailable and by expected value when odds are present. The separation between predicted score (most likely scoreline) and MENSIONE pick (recommended market) is explicit in the data structures, the API schema, and the wire format. Predicted score is contextual information nested inside the pick; it never substitutes for the pick.

Prediction versioning creates UUID-identified immutable snapshots at lifecycle stages (7d before, 24h before, lineup confirmed, kickoff, live). Versions are never modified after creation. Duplicate stage writes raise ValueError unless explicitly allowed. The manager supports both in-memory and persistence-backed storage, but immutability enforcement checks only the manager's local state, not the persistence layer, introducing a gap where concurrent processes or crash-recovery scenarios could write duplicate stages to the database.

Change attribution decomposes prediction deltas into proportional factors (lineup, form, xG, tactical, model update, data quality). Factors are normalized to sum to 1.0, but the normalization step divides by total magnitude without checking for zero, risking NaN propagation if all factor magnitudes are zero (unlikely but possible if two predictions are identical).

Track record records all prediction outcomes—no cherry-picking logic exists. Brier score, log loss, accuracy, and ROI are calculated from the full set. ROI calculation assumes a losing bet contributes zero return but doesn't explicitly handle the edge case where all predictions lose and total return is zero, potentially causing divide-by-zero if stakes are also miscounted.

The service pipeline calls `generate_full_prediction()`, which runs Poisson, derives markets via MarketDerivationEngine, generates the pick via MensionePickGenerator, versions the prediction, and enriches AnalysisContext with `predicted_score`, `mensione_pick`, and `prediction_version_id` fields. The API endpoint at `/api/v1/matches/{match_id}/prediction` returns all three fields in the response schema. Backward compatibility is preserved: existing AnalysisContext fields remain, Easy Match detection still runs, and the AI Analyst receives the same structure plus the new fields.

Verification evidence shows 849 tests collected, 825 passing, 24 skipped (database integration tests), 0 failures. Two new tests were added for immutability enforcement with mock persistence. The tests confirm duplicate stage writes raise ValueError and that the persistence service is invoked, but they mock the persistence layer rather than exercising a real database round-trip.

<summary>Issues (3)</summary>

1. **Immutability gap with concurrent writers** — PredictionVersionManager.create_version() checks `get_version_by_stage()` before writing, but get_version_by_stage() reads from persistence if available and writes to persistence immediately after. A concurrent process writing the same stage between the read check and the write will not be caught. Add a unique constraint on (match_id, stage) in the persistence schema and handle the database-level conflict.

2. **ChangeAttributionEngine factor normalization zero-division** — Line 168 in change_attribution.py divides factor magnitudes by `total_magnitude` without checking if total is zero. If all detected factors have zero magnitude (or no factors detected but an empty list is passed to normalization), dividing by zero produces NaN. Guard with `if total_magnitude > 0` before the division loop.

3. **TrackRecord ROI calculation edge case** — `_calculate_roi()` in track_record.py calculates `(total_return - total_stake) / total_stake`. If all predictions lose, total_return is 0 and the result is -1.0 (100% loss), which is correct. But if `results_with_odds` is somehow empty after filtering (defensive case), `total_stake` is 0 and division by zero occurs. This is already guarded by the early return when `results_with_odds` is empty, so the issue is unlikely. Document the invariant or add an assertion that total_stake > 0 before the division.

## Market derivation mathematical consistency

MarketDerivationEngine.derive() normalizes the score distribution to sum to 1.0, then derives every market by summing scorelines that satisfy each outcome. 1X2 sums where home > away, home == away, home < away, then renormalizes to eliminate floating-point drift. Double-chance are sums of 1X2. Over/under sum where total goals exceed or don't exceed each line, then normalize each pair. BTTS sums where both teams scored vs. at least one didn't. Team totals sum by individual team thresholds. Asian handicaps adjust by the line and classify as home win, push, away win. Exact score returns top N by probability.

The `validate()` method confirms 1X2 sums to 1.0 (within 0.001), double-chance values match 1X2 sums (1X == home + draw, X2 == draw + away, 12 == home + away), BTTS sums to 1.0, and each over/under pair sums to 1.0. Validation raises ValueError on failure, preventing inconsistent probabilities from propagating.

## MENSIONE pick vs predicted score separation

MensionePick dataclass includes `pick_market` ("HOME OVER 1.5"), `pick_probability`, `confidence_label`, `confidence_score`, optional EV/edge if odds available, reasoning factors, and two context fields: `predicted_score` (most likely scoreline) and `score_distribution_top5`. The predicted score is nested as context, not a recommendation.

MensionePickGenerator._build_market_rankings() creates a MarketRanking for every outcome: HOME/DRAW/AWAY, 1X/X2/12, OVER/UNDER per line, BTTS YES/NO, HOME OVER/AWAY OVER for team totals. Conviction is distance from threshold (0.333 for 1X2, 0.667 for double chance, 0.5 for binary). With odds: EV = (prob * odds) - 1, edge = model_prob - implied_market_prob, score = EV + edge. Without odds: score = conviction.

generate() filters by minimum probability (0.55) and edge (0.0 if odds), sorts by score descending, selects top market, builds reasoning from probability/confidence/edge/EV/agreement/quality, constructs MensionePick with predicted score from exact_score_top.

MatchPredictionResponse schema has three distinct top-level fields: `predicted_score`, `mensione_pick`, `prediction_version_id`. Endpoint populates all three from AnalysisContext. Wire format preserves the distinction.

## Prediction versioning immutability and the enforcement gap

PredictionVersion holds UUID version_id, match_id, stage enum (7d_before, 24h_before, lineup_confirmed, kickoff, live), created_at, and prediction_data dict (probabilities, xG, markets, mensione_pick, confidence). Prediction_data is deep-copied on construction to prevent external mutation.

PredictionVersionManager.create_version() checks get_version_by_stage() at line 133, raises ValueError if version exists and allow_stage_overwrite=False, creates version, saves via persistence_service.save_version() at line 152, or appends to in-memory list.

The gap: get_version_by_stage() queries persistence at line 165. Between check at 133 and save at 152, a concurrent process could write (match_id, stage). Manager won't detect the race. Persistence needs a unique constraint on (match_id, stage) to catch this. Current implementation assumes single-threaded access.

test_prediction_versioning.py uses MockPersistenceService (dict-backed). Test creates version, attempts duplicate, asserts ValueError. Confirms manager logic in synchronous single-process case. Doesn't test concurrent writers or database-level enforcement.

## Change attribution factor sum and normalization

ChangeAttributionEngine.attribute() calculates total change in home_win_probability. If below threshold (0.02), returns empty factors list. Otherwise calls _detect_factors() to identify lineup, form, xG, tactical, model update, data quality changes. Each returns Optional[AttributionFactor] with unnormalized magnitude. If no factors detected, fallback adds OTHER with magnitude 1.0 (line 262).

Line 168 normalization: sum magnitudes, divide each by total. If total_magnitude is zero (all factors have 0.0 magnitude, or fallback skipped), division produces NaN. Fallback at 262 should prevent this, but if _detect_factors() is modified or factor with 0.0 added, bug surfaces.

attribution.validate() at 176 checks factors sum to 1.0 within tolerance (0.99-1.01) if non-empty. Empty factors (below-threshold change) passes. NaN magnitudes would make sum NaN, validation raises ValueError, catching bug too late.

Factor detection returns heuristic magnitudes: lineup 0.4 (confirmation) or 0.3 (change > 0.05), form 0.2 (model added), xG proportional to change capped at 0.5, tactical 0.15 (added) or 0.2 (adjustment > 0.1), model update 0.3, data quality 0.15 (score change > 0.1). Normalization makes them proportional.

## Track record transparency and ROI edge case

TrackRecordManager.record_outcome() creates PredictionResult with predicted probs, actual outcome/scores, optional market predictions/actuals/odds, metadata. Saves to persistence or appends to memory. No filtering: all outcomes recorded including wrong/low-confidence/missing-data predictions.

_calculate_brier_score() creates one-hot vector for actual, calculates squared error for each 1X2 outcome, sums, averages. _calculate_log_loss() takes log of predicted probability of actual (clipped to [0.0001, 0.9999]), negates, averages. _calculate_accuracy() finds most probable predicted outcome, compares to actual.

_calculate_roi() filters to results_with_odds (line 369). If none, returns None. Otherwise `total_stake = len(results_with_odds)` (one unit per bet). For each: find most probable predicted outcome, retrieve odds, if correct add odds to total_return, if wrong add nothing. `roi = (total_return - total_stake) / total_stake`.

All predictions wrong: total_return = 0, roi = -1.0 (100% loss), correct. Edge case: results_with_odds empty after filter, total_stake = 0, division by zero at line 398. Already guarded by early return at 372: if results_with_odds empty, returns None before calculation. Invariant: if roi calculated, total_stake > 0. Code correct, lacks explicit assertion/comment.
