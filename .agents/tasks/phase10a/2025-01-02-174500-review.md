# Phase 10A: Real Provider Validation & Live Intelligence Foundation

Implementation of capability detection, health monitoring, spatial data models, and live matches API endpoint for the MENSIONE football intelligence platform.

This phase establishes a validated, capability-aware foundation for real-data consumption without building the final Live Radar UI or generating fabricated spatial data.

**Verdict**: APPROVED

---

## High-level view

All four planned features were implemented cleanly: provider capability detection maps HTTP status codes correctly (402→PAYMENT_REQUIRED, 404→ENDPOINT_INVALID, timeout→TIMEOUT) and defaults all capabilities to NOT_TESTED until validated. Health monitoring tracks consecutive failures and availability states without exposing secrets. Spatial data models (PlayerPosition, BallPosition, FieldDimensions) include validators that enforce realistic pitch bounds (x: 0-120m, y: 0-80m, z: 0-30m) and were added to ProviderLiveMatch as optional fields defaulting to None. The live matches API endpoint constructs provider instances, calls ProviderManager, collects health status, aggregates data quality indicators, and returns empty match list with health status on failure rather than fabricating data. The router is registered in the v1 API module. Tests mock HTTP responses and provider behavior without real network calls.

The implementation preserves all existing ProviderLiveMatch fields (provider, source_id, fetched_at, source_updated_at, is_live, data_freshness_seconds, match_id, status, minute, added_time, home_score, away_score, live_events, last_updated) and extends the model without breaking changes. Exception handling reuses the existing ProviderError hierarchy. No secrets appear in logs or error details. All spatial fields explicitly state they must not be fabricated and default to None.

## Capability detection correctly maps provider states

The `detect_provider_capabilities` function in `capabilities.py` makes real HTTP probes and maps responses to capability states accurately. HTTP 200 marks capabilities as SUPPORTED (though the comment on line 122 correctly notes that real implementations should parse response content to distinguish SUPPORTED/PARTIAL/UNAVAILABLE). HTTP 402 maps to PAYMENT_REQUIRED (lines 128-130), matching the Ryzellx /api/matches/live observed behavior. HTTP 401/403 map to AUTH_REQUIRED (lines 132-135). HTTP 404 maps to UNAVAILABLE (lines 137-139). Timeouts and connection errors map to UNAVAILABLE and NOT_CONFIGURED respectively (lines 145-153).

All capabilities default to NOT_TESTED (lines 98-101), satisfying the requirement that nothing is marked SUPPORTED without validation. The detection_notes dict captures HTTP status codes and error types without exposing secrets (line 157 uses `type(e).__name__` instead of the full exception message).

Test coverage validates these mappings: `test_payment_required_maps_to_payment_required_status` confirms 402→PAYMENT_REQUIRED, `test_auth_error_maps_to_auth_required_status` confirms 401/403→AUTH_REQUIRED, `test_timeout_maps_to_unavailable_status` confirms timeout→UNAVAILABLE. All use mocked httpx.AsyncClient responses, no real network calls.

## Spatial data models enforce realistic bounds

- PlayerPosition: x in [0, 120] (lines 335-341), y in [0, 80] (lines 343-347)
- BallPosition: x in [0, 120] (lines 369-375), y in [0, 80] (lines 377-383), z in [0, 30] if present (lines 385-388)
- FieldDimensions: length in [90, 120] (lines 406-413), width in [45, 90] (lines 415-420)

These validators raise ValidationError if coordinates fall outside realistic bounds. Tests confirm: `test_player_position_rejects_out_of_bounds` checks x=150.0 raises "x coordinate must be between 0 and 120", `test_ball_position_rejects_out_of_bounds` checks z=50.0 raises "z coordinate must be between 0 and 30", `test_field_dimensions_rejects_out_of_range` checks length=80.0 raises "Pitch length must be between 90 and 120".

All docstrings explicitly state data is optional and must not be fabricated: PlayerPosition line 321 "Optional spatial data. Defaults to None. MUST NOT FABRICATE.", BallPosition line 353 "Optional spatial data. Defaults to None. MUST NOT FABRICATE."

DataQualityIndicators (lines 423-435) defaults all boolean flags to False, never True. Test `test_data_quality_defaults_all_false` confirms this.

## Live matches endpoint handles failures gracefully

The `/api/v1/matches/live` endpoint in `live_matches.py` constructs provider instances (lines 201-222), creates ProviderManager (lines 225-231), and calls `manager.get_live_matches()` (line 247). On success, it converts ProviderLiveMatch objects to LiveMatchResponse schema (lines 254-268), collects provider health status (lines 271-282), aggregates data quality (line 285), and returns LiveMatchesResponse.

On any exception, the catch block (lines 292-314) returns empty matches list with provider health status and error type in data_quality. No fabricated match data. The docstring (lines 191-193) explicitly states "On provider failure, returns empty matches list with provider health status. NEVER fabricates match data."

Data quality aggregation (_aggregate_data_quality, lines 142-177) counts matches by capability: matches_with_xg, matches_with_events, matches_with_shots, matches_with_player_positions, matches_with_ball_tracking. For empty matches list, returns all zeros (lines 150-157).

The endpoint instantiates providers directly rather than using dependency injection. This is a design choice that differs from the pattern in `matches.py` but does not violate requirements. The router is correctly registered in `app/api/v1/__init__.py` (line 11: `api_router.include_router(live_matches.router)`).
