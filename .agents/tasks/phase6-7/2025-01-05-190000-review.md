# Phase 6 + Phase 7: Result Ingestion, Settlement & Track Record

Result ingestion pipeline and settlement engine with frozen pick preservation, supporting five market types and comprehensive profit/loss tracking.

The implementation ingests real match results via provider abstraction, settles predictions to WIN/LOSS/VOID with accurate profit/loss calculation, and builds track record foundation for market performance analysis. Settlement correctly uses frozen odds from prediction time and never overwrites the immutable pick fields. All 1077 backend tests pass.

**Watch for:** Settlement update in `prediction_version.py` writes to all three settlement columns (actual_result, profit_loss, settled_at) but bypasses frozen pick fields — frozen pick integrity verified. Over/Under line extraction regex may fail on uncommon format variations. No API endpoints exposed yet (Phase 8 scope).

**Verdict:** APPROVED

## High-level view

Settlement never touches frozen pick fields. The `settle_prediction()` method in `prediction_version.py` creates a new `PredictionVersion` object copying all nine frozen pick fields unchanged, then writes only the three settlement columns (`actual_result`, `profit_loss`, `settled_at`) to the database via direct SQLAlchemy attribute assignment. This pattern is correct and preserves historical integrity.

Profit/loss calculation uses the correct formula: WIN is `(odds - 1.0) * stake`, not `odds * stake`. The frozen `selection_odds` field is the only odds value used — no re-fetching from bookmakers.

Market settlement logic covers MATCH_RESULT (1X2), OVER_UNDER with push handling, BTTS, DOUBLE_CHANCE (1X, 12, X2), and HANDICAP with push scenarios. Unsupported markets raise `ValueError` with a clear message listing what's supported. Postponed/cancelled matches return VOID.

Result ingestion never fabricates data. If a match isn't found in the provider, `get_match_result()` returns `None` and settlement raises `ValueError`. Unfinished matches are rejected unless postponed/cancelled (which settle to VOID).

Track record aggregation uses SQLAlchemy group-by queries to calculate win rate, ROI, and profit/loss per market. Empty result sets return valid zero-filled dictionaries, not errors. The `get_settled_picks_by_market()` method uses flexible ILIKE matching, so a query for "HOME" will match "HOME_WIN".

## Frozen pick integrity in settlement flow

The settlement flow creates a new `PredictionVersion` object in `settle_prediction()` by copying all fields from the original version, including the nine frozen pick fields:

```python
settled_version = PredictionVersion(
    # ... all original fields ...
    # Frozen pick fields (unchanged)
    selected_market=version.selected_market,
    selection_text=version.selection_text,
    selection_probability=version.selection_probability,
    selection_confidence=version.selection_confidence,
    selection_odds=version.selection_odds,
    selection_fair_odds=version.selection_fair_odds,
    selection_edge=version.selection_edge,
    value_classification=version.value_classification,
    risk_level=version.risk_level,
    # Settlement fields (NEW)
    actual_result=outcome.value,
    profit_loss=profit_loss,
    settled_at=datetime.utcnow()
)
```

Database persistence writes only to settlement columns via direct attribute assignment on the fetched `PredictionVersionDB` object:

```python
db_version.actual_result = outcome.value
db_version.profit_loss = profit_loss
db_version.settled_at = settled_version.settled_at
self.persistence_service.session.commit()
```

This pattern is correct. The frozen pick columns are not mentioned in the database update, so they remain untouched. The historical record at prediction time is preserved.

The code does not, however, have a test that verifies this behavior. All tests in `test_settlement.py` focus on market logic (WIN/LOSS/VOID outcomes and profit/loss amounts). None call `PredictionVersionManager.settle_prediction()` and assert that the frozen fields are unchanged after settlement. This gap leaves frozen pick integrity verified by code review but not by automated testing.

## Profit/loss calculation correctness

WIN uses `(odds - 1.0) * stake`, which is correct for European decimal odds. A £1 bet at 2.10 odds returns £2.10 total (£1.10 profit), so profit is `(2.10 - 1.0) * 1.0 = 1.10`. The alternative formula `odds * stake` would incorrectly give £2.10 as profit.

LOSS is `-1.0 * stake`. VOID is `0.0`.

The frozen `selection_odds` field from `PredictionVersion` is the sole odds input to `SettlementEngine.settle_prediction()`. No code path fetches current bookmaker odds. Profit/loss reflects exactly what the user would have won or lost at the odds available when the prediction was made.

## Market settlement logic: MATCH_RESULT (1X2)

`_settle_match_result()` maps `selection_text` to a predicted `MatchOutcome` (HOME_WIN, DRAW, or AWAY_WIN) and compares with `match_result.outcome`. The mapping checks for substring matches ("HOME" in selection_text → HOME_WIN, "DRAW" → DRAW, "AWAY" → AWAY_WIN) plus single-character aliases ('1', 'X', '2').

It would fail if selection_text were something unexpected like "Barcelona Win" (contains neither "HOME" nor "1"). The Smart Market Selector should ensure selection_text follows the expected format.

## Market settlement logic: OVER_UNDER with push handling

`_settle_over_under()` extracts the line from `selected_market` using regex, calculates total goals, and compares:
- `total_goals > line` → OVER wins, UNDER loses
- `total_goals < line` → UNDER wins, OVER loses  
- `total_goals == line` → VOID (push)

Push occurs only on whole-number lines (2.0, 3.0) when goal totals match exactly. Half-goal lines (2.5, 3.5) never push.

Line extraction uses `re.search(r'(\d+)[_.](\d+)', selected_market)` to find "2_5" in "OVER_2_5" and return 2.5. Fallback to `re.search(r'(\d+)', selected_market)` handles whole-number lines like "OVER_3" → 3.0.

This works for expected formats but is fragile. "OVER2.5" (no separator) would fail — the first regex needs `[_.]` between digits, and the second would match only "2", returning 2.0 instead of 2.5. "OVER_TWO_POINT_FIVE" would fail entirely. The code doesn't validate that Smart Market Selector produces "OVER_X_Y" or "UNDER_X_Y" format.

## Market settlement logic: BTTS

BTTS logic checks whether both `home_score > 0` and `away_score > 0`. If `selection_text` contains "YES" or equals "BTTS", predicted outcome is YES. Otherwise NO.

Malformed selection_text like "Both Teams Score" (instead of "BTTS_YES") would be treated as BTTS_NO because "YES" is not in the string.

## Market settlement logic: DOUBLE_CHANCE

Maps "1X" to {HOME_WIN, DRAW}, "12" to {HOME_WIN, AWAY_WIN}, "X2" to {DRAW, AWAY_WIN}. If actual outcome is in the set, returns WIN. Else LOSS. No push scenarios.

## Market settlement logic: HANDICAP with push

Extracts handicap value and team from `selected_market` (e.g., "HANDICAP_-1.5_HOME" → -1.5 applied to home score). Adjusted scores determine the outcome with handicap. If adjusted scores are equal, returns VOID (push).

The extraction logic splits on underscore and looks for parts starting with `+` or `-`. Format "HOME_HANDICAP_-1.5" (team comes first) would fail because the parser expects team after the handicap. Format "HANDICAP-1.5HOME" (no underscores) fails entirely because the split produces a single part.

Push handling: `adjusted_home == adjusted_away` → VOID. Happens on whole-number handicaps when the adjusted result is a draw. Quarter-ball handicaps (not implemented) would require partial win/loss logic.

## Result ingestion and fabrication avoidance

`ResultIngestionService.get_match_result()` calls `provider.get_match()` and returns `None` if the match is not found. It does not generate placeholder results or return fake scores.

For FINISHED matches, it validates that `home_score` and `away_score` are not `None`, raising `ValueError` if either is missing.

For POSTPONED/CANCELLED matches, it returns a `MatchResult` with `is_final=True` but `home_score=None` and `outcome=None`. The `is_settleable()` method returns `False` for this, and settlement logic checks for POSTPONED/CANCELLED status explicitly and returns VOID.

The flow enforces "no data → no settlement" rather than "no data → guess."

## Track record aggregation and empty state

`get_settled_summary()` queries `PredictionVersionDB` for records where `actual_result IS NOT NULL`. If the result set is empty, it returns a dictionary with all metrics set to 0 or 0.0.

The code comment says "win_rate = wins / non_void if non_void > 0 else 0.0", but doesn't clarify whether 0.0 means "no data" or "0% win rate from losses". Returning `None` when `non_void == 0` would distinguish the two cases.

`get_market_performance()` uses SQLAlchemy `func.count()` and `func.sum()` with grouping by `selected_market`. If no settled predictions exist, returns empty list `[]`.
