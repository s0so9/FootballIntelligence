# MENSIONE Canonical Pipeline Integration

Integration of canonical feature snapshot, model orchestration, ensemble, calibration, and confidence assessment into a unified prediction pipeline.

**Watch for:** The canonical pipeline components were built but never integrated into PredictionService. The service still uses the old Poisson-only approach with hardcoded confidence values. ModelOrchestrator, FeatureSnapshot, EnsembleIntegration, CalibrationIntegration, and ConfidenceIntegration exist as isolated implementations but are not called by the production prediction endpoint.

**Verdict**: NEEDS_CHANGES

## High-level view

The coder built the canonical pipeline components as specified — MatchFeatureSnapshot for unified feature representation, ModelOrchestrator for multi-model execution, EnsembleEngine with ReliabilityWeights, IsotonicCalibration for probability calibration, and ConfidenceEngine with six weighted components. All seven models (Poisson, Dixon-Coles, Elo, Monte Carlo, Negative Binomial, Form-Adjusted, Logistic Regression) are registered in ModelOrchestrator.create_default_registry(). Tests exist for each component in isolation.

The fatal gap: PredictionService never imports or calls any of these components. The production endpoint at GET /matches/{match_id}/prediction still calls `prediction_service.generate_full_prediction()`, which directly invokes the old Poisson-only path. The canonical pipeline exists as dead code — compilable, testable in isolation, but unreachable from the API.

ConfidenceEngine does accept real parameters (model_agreement, data_quality_score, n_matches, brier_score, lineup_status) and computes confidence from six weighted components. But PredictionService.generate_full_prediction() calls it with hardcoded values: model_agreement=1.0 (line 757), data_quality_score=0.7 (line 758), n_matches fabricated from feature key count (line 755), and bypasses the orchestration/ensemble/calibration stack entirely.

Model agreement is calculated correctly in EnsembleEngine._calculate_agreement() as 1 - (std_dev * 3), not hardcoded. DataQualityEngine exists and can produce real scores. But none of this machinery is invoked because PredictionService doesn't wire to ModelOrchestrator.

The integration layer classes (EnsembleIntegration, CalibrationIntegration, ConfidenceIntegration) exist in model_orchestrator.py to bridge orchestration results to their respective engines. They're designed correctly but never instantiated in production code.

<summary>Issues (8)</summary>

1. **Canonical pipeline never wired** — PredictionService doesn't import or instantiate ModelOrchestrator, EnsembleIntegration, CalibrationIntegration, or ConfidenceIntegration. Production code path bypasses the entire canonical stack. Wire PredictionService.__init__() to create these components and replace generate_full_prediction() to call the orchestrator → ensemble → calibration → confidence flow.

2. **FeatureSnapshot extraction not implemented** — MatchFeatureSnapshot exists but extract_feature_snapshot() is never called. PredictionService still uses MatchFeatureExtractor.extract_features() returning a flat dict, bypassing the canonical snapshot. Replace feature extraction with extract_feature_snapshot() and pass MatchFeatureSnapshot to ModelOrchestrator.run_all().

3. **Hardcoded confidence inputs** — PredictionService.generate_full_prediction() line 757-760 calls confidence_engine.assess() with model_agreement=1.0, data_quality_score=0.7, and n_matches fabricated from feature dict keys. These are the exact placeholder values the spec forbids. Replace with orchestration_result.model_agreement, snapshot.data_quality_report.overall_score, and snapshot.home_form.matches_analyzed.

4. **No reuse of PipelineResult** — The spec requires "one pipeline execution result reused by prediction/markets/confidence/pick/analysis". PredictionService runs separate feature extraction for generate_prediction(), generate_prediction_markets(), detect_easy_match(), and build_analysis_context(). Create a PipelineResult dataclass containing snapshot, orchestration_result, ensemble_prediction, calibrated_prediction, confidence_assessment, and market_probs, then derive all downstream outputs from it.

5. **Ensemble agreement not computed from models** — EnsembleEngine._calculate_agreement() correctly computes 1 - (std_dev * 3) from model probabilities, but this is never surfaced because PredictionService doesn't call EnsembleIntegration.combine_predictions(). The hardcoded model_agreement=1.0 in line 757 bypasses real computation. Wire ensemble result's metadata["model_agreement"] into confidence assessment.

6. **DataQualityEngine unused** — data_quality.py and DataQualityEngine exist (imported in feature_snapshot.py), but PredictionService never instantiates or calls it. The snapshot's data_quality_report field stays None, so ConfidenceIntegration._extract defaults to 0.5 in line 552. Instantiate DataQualityEngine in PredictionService and populate snapshot.data_quality_report before orchestration.

7. **Calibration never fitted** — Calibrator1X2 in model_orchestrator.py wraps three IsotonicCalibration instances, but CalibrationIntegration.create_default() creates an unfitted calibrator and PredictionService never calls fit(). The calibrate_prediction() method falls back to uncalibrated probabilities. This is acceptable for Phase 1 (insufficient historical data) but the integration layer should expose is_fitted status in metadata so confidence assessment knows calibration isn't trained.

8. **API backward compatibility untested** — The spec requires "Keep existing prediction API contracts compatible" and "Do not break existing frontend consumers." Tests in test_api_matches.py verify the response structure, but no test confirms the new pipeline (once wired) produces the same JSON schema as the old Poisson-only path. Add a test comparing old vs new response schemas before deployment.

## Canonical components exist but are isolated

The repository contains complete implementations of all specified pipeline components: MatchFeatureSnapshot (feature_snapshot.py), ModelOrchestrator (model_orchestrator.py lines 123-327), EnsembleEngine with ReliabilityWeights (ensemble_engine.py lines 106-231), IsotonicCalibration (calibration_engine.py lines 82-130), ConfidenceEngine with six weighted components (confidence_engine.py lines 83-209), DataQualityEngine (data_quality.py), and integration wrappers (EnsembleIntegration, CalibrationIntegration, ConfidenceIntegration in model_orchestrator.py lines 329-682).

ModelOrchestrator.create_default_registry() registers seven models: Poisson, Dixon-Coles, Elo, Monte Carlo, Negative Binomial, Form-Adjusted, Logistic Regression (model_orchestrator.py lines 308-327). Each model implements the PredictionModel interface (interfaces.py) with predict(), check_requirements(), and get_metadata(). The orchestrator's run_all() method executes all compatible models from a MatchFeatureSnapshot, categorizes outputs as SUPPORTED_RUN / UNAVAILABLE_MISSING_INPUTS / FAILED, and returns ModelOrchestrationResult with separate lists for successful_predictions, unavailable_models, and failed_models (model_orchestrator.py lines 154-195).

Tests exist for each component in isolation: test_model_orchestrator.py (348 lines), test_ensemble_engine.py, test_calibration_engine.py, test_confidence_engine.py, test_feature_snapshot.py. The test for ModelOrchestrator.create_default_registry() confirms all seven models are registered (test_model_orchestrator.py line 327). Test for partial failure confirms one model's exception doesn't kill the pipeline (line 300).

The integration gap: PredictionService never imports ModelOrchestrator, MatchFeatureSnapshot, or any integration class. Searching app/prediction/service.py for these symbols returns zero matches. The production endpoint calls PredictionService.generate_full_prediction() (matches.py line 378), which extracts features via the old MatchFeatureExtractor.extract_features() (service.py line 754), runs only PoissonModel directly (line 235-268), and calls confidence_engine.assess() with hardcoded inputs (line 757-763).

## PredictionService still uses Poisson-only path

PredictionService.generate_full_prediction() (service.py lines 715-872) implements a "Phase 1" pipeline: run Poisson → derive markets → assess confidence → generate pick → version → return AnalysisContext. The comment at line 723 states "Simplified Phase 1 pipeline: Poisson → Markets → Pick → Versioning."

This method calls self.generate_prediction(match) (line 751), which extracts features from MatchFeatureExtractor (line 211), directly calculates Poisson lambda values (lines 229-246), and calls poisson_model.predict_from_lambda() (line 249). The result is a single Prediction object, not a ModelOrchestrationResult.

Confidence assessment at lines 757-763:
```python
confidence_assessment = self.confidence_engine.assess(
    model_agreement=1.0,  # Single model, perfect "agreement"
    data_quality_score=0.7,  # Default moderate quality
    n_matches=max(5, n_matches),  # Assume at least 5 matches
    brier_score=None,  # No calibration yet
    lineup_status="expected",
    recent_predictions=None
)
```

These are the exact hardcoded placeholder values the spec forbids. Rule 3 in the review prompt: "Is ConfidenceEngine using real pipeline values — not hardcoded data_quality_score=0.7 or model_agreement=1.0?" Confirmed: NO. The confidence inputs are fabricated.

The n_matches calculation at line 755 is also fabricated: `n_matches = sum(1 for k, v in features.items() if v is not None and 'strength' in k)`. This counts feature dict keys containing "strength", not the actual match sample size from form data.

ConfidenceEngine itself is correctly implemented. It accepts the six parameters (model_agreement, data_quality_score, n_matches, brier_score, lineup_status, recent_predictions) and computes weighted average across six components (confidence_engine.py lines 104-143). The issue is that PredictionService never provides real values from the orchestration pipeline.

## FeatureSnapshot not extracted

MatchFeatureSnapshot is a comprehensive dataclass (feature_snapshot.py lines 148-299) with TeamStrengthMetrics, FormMetrics, PlayerAvailability, LeagueContext, TacticalContext, SourceProvenance, MarketInformation, and DataQualityReport. The get_feature_dict() method (lines 215-275) converts the snapshot to a flat dict compatible with existing models.

The factory function extract_feature_snapshot() (lines 301-400) accepts match_id, team IDs, feature_set from FeatureAggregator, data_quality_report, and optional market_info, then populates the snapshot. It extracts home/away form from feature_set.home_form / away_form (lines 342-374) and attack/defence metrics into TeamStrengthMetrics (lines 376-397).

PredictionService never calls this function. It still uses MatchFeatureExtractor.extract_features() (line 211), which returns a flat dict without SourceProvenance, DataQualityReport, or structured TeamStrengthMetrics. The snapshot's data_quality_report field would remain None, causing ConfidenceIntegration._extract to default to 0.5 (model_orchestrator.py line 552).

ModelOrchestrator.run_all() expects a MatchFeatureSnapshot (model_orchestrator.py line 155) and calls snapshot.get_feature_dict() (line 176) to convert to the flat dict format for model compatibility. This design allows the canonical snapshot to coexist with existing models that expect flat dicts. But PredictionService never constructs the snapshot, so ModelOrchestrator is never called.

## Model agreement computed but never used

EnsembleEngine._calculate_agreement() (ensemble_engine.py lines 243-269) extracts home_win_prob from all predictions, calculates mean and standard deviation, and returns `max(0.0, 1.0 - (std_dev * 3.0))`. When all models agree perfectly (std_dev=0), agreement=1.0. When models maximally disagree (std_dev≈0.33), agreement≈0.0.

The ensemble result's metadata includes "model_agreement": agreement_score (line 230). EnsembleIntegration.combine_predictions() (model_orchestrator.py lines 362-403) wraps EnsembleEngine.combine() and logs the agreement (line 399). ConfidenceIntegration.assess_confidence() extracts agreement from ensemble_prediction.metadata.get("model_agreement", 0.0) (line 585) and passes it to ConfidenceEngine.assess().

This chain is correctly designed: orchestration → ensemble → extract agreement → confidence. But PredictionService bypasses it entirely. The hardcoded model_agreement=1.0 in service.py line 757 is never replaced with the real computed value.

Searching service.py for "EnsembleIntegration" or "orchestration_result" returns zero matches. The integration classes exist but are never instantiated.

## DataQualityEngine exists but unused

data_quality.py defines DataQualityEngine (lines 85-193) with check_quality() method that accepts match_id, features dict, and optional source_metadata, then runs multiple DataQualityCheck instances (CompletennessCheck, ConsistencyCheck, ReasonablenessCheck, RecencyCheck). It returns DataQualityReport with overall_score, checks list, and metadata.

feature_snapshot.py imports DataQualityReport (line 9) and MatchFeatureSnapshot has a data_quality_report: Optional[DataQualityReport] field (line 194). The extract_feature_snapshot() function accepts data_quality_report as a parameter (line 307) and assigns it to the snapshot (line 334).

PredictionService never instantiates DataQualityEngine. Searching service.py for "DataQuality" returns zero matches. The snapshot's data_quality_report would be None if extract_feature_snapshot() were called, unless the caller (PredictionService) passed a populated report.

ConfidenceIntegration.assess_confidence() extracts data_quality_score from snapshot.data_quality_report.overall_score if available, else defaults to 0.5 (model_orchestrator.py lines 590-592). This fallback is reasonable, but the issue is that PredictionService.generate_full_prediction() bypasses the snapshot entirely and hardcodes data_quality_score=0.7 (service.py line 758).

## Calibration integration exists but unfitted

CalibrationIntegration (model_orchestrator.py lines 471-527) wraps Calibrator1X2, which contains three IsotonicCalibration instances for home/draw/away probabilities (lines 423-468). The calibrate_prediction() method (lines 489-525) calls calibrator.calibrate_1x2() and marks the result with calibration_status: "calibrated" or "uncalibrated_fallback".

CalibrationIntegration.create_default() (lines 529-536) returns a new instance with an unfitted Calibrator1X2. IsotonicCalibration.fit() (calibration_engine.py lines 82-113) requires at least 50 samples (MIN_SAMPLES=50). Without historical data, the calibrator remains unfitted and calibrate() returns the uncalibrated probability with a warning (lines 126-128).

This is acceptable for Phase 1 — the spec acknowledges "If historical fitting is unavailable, use the repository's existing deterministic/default weighting mechanism and expose that limitation clearly." The calibration_status metadata correctly indicates "uncalibrated_fallback" when is_fitted=False.

The issue is that PredictionService never instantiates CalibrationIntegration, so even this fallback path is unreachable. The service returns raw Poisson probabilities without attempting calibration.

## Pipeline result not reused

The spec states: "Create a single pipeline execution result that can be reused by: prediction, markets, easy match, confidence, MENSIONE Pick, analysis context, API response."

PredictionService.generate_full_prediction() (service.py lines 715-872) calls:
1. self.generate_prediction(match) — runs Poisson (line 751)
2. self.market_derivation_engine.derive() — derives markets from score dist (line 748)
3. self.confidence_engine.assess() — assesses confidence (line 757)
4. self.mensione_pick_generator.generate() — generates pick (line 770)
5. self.generate_prediction_markets() — regenerates markets for AnalysisContext (line 864)
6. self.build_analysis_context() — builds context (line 867)

Each of these methods independently extracts features via self.feature_extractor.extract_features(match) (lines 211, 480, 549, 632). Feature extraction happens at least four times for one prediction request.

The spec requires a PipelineResult dataclass containing snapshot, orchestration_result, ensemble_prediction, calibrated_prediction, confidence_assessment, market_probs. All downstream consumers should derive from this single result.

No PipelineResult dataclass exists. Searching the repository for "PipelineResult" returns zero matches (confirmed: grep_search earlier found no matches).

## API backward compatibility not verified

The GET /matches/{match_id}/prediction endpoint (matches.py line 333) returns MatchPredictionResponse schema (lines 336-337) containing home_win_probability, draw_probability, away_win_probability, home_xg, away_xg, btts_probability, predicted_score, mensione_pick, prediction_version_id, market_analysis, easy_match, is_development_data.

No test confirms the new canonical pipeline (once wired) produces the same JSON schema. The spec requires "Keep existing prediction API contracts compatible" and "Do not break existing frontend consumers." Once PredictionService is refactored to call ModelOrchestrator, a test should verify the response schema remains unchanged (same fields, same types, same ranges) even though the computation path differs.

The risk: if the canonical pipeline produces ensemble probabilities that differ from Poisson-only probabilities, frontend clients might break on unexpected values. A schema validation test would catch this before deployment.
