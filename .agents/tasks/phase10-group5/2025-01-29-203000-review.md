# Phase 10 Group 5 Implementation Review

Market-specific modeling infrastructure and uncertainty assessment for MENSIONE football intelligence platform.

**Verdict**: CHANGES_REQUESTED

Group 5 adds market-specific feature eligibility, shot market prediction infrastructure, model disagreement analysis, uncertainty assessment, and market reliability calculation. The architecture cleanly extends the existing seven-model ensemble without duplication. Backward compatibility is maintained through Optional fields and default parameters. Tests demonstrate core functionality.

Three blocking concerns require fixes: hardcoded uncertainty component weights without justification, missing VERY_HIGH uncertainty filtering in market selector logic, and shot market engine stub that doesn't verify distribution selection. One architectural gap: market-specific feature eligibility doesn't connect to the actual prediction pipeline.

**Watch for:** Uncertainty component weights lack empirical justification (confirmed), VERY_HIGH uncertainty level check is incomplete in market selector (confirmed), shot distribution selection documented but not implemented (confirmed), feature eligibility system has no integration path to models (confirmed).

## High-level view

Market-specific feature eligibility defines nine market types with eligible feature lists, but the feature selector only extracts values from snapshots without connecting to model prediction—models still receive the full MatchFeatureSnapshot, making eligibility mappings advisory documentation rather than enforced constraints.

Shot market engine defines threshold probability calculation from Poisson/Negative Binomial distributions but leaves the entire predict_all_shot_markets method as a stub returning empty dict, so no shot market predictions are actually generated.

Model disagreement analyzer extracts probability dispersion from ModelPrediction lists, using the existing EnsembleEngine agreement formula (1 - std * 3) clamped to [0,1], providing transparent disagreement quantification from already-available model outputs.

Uncertainty engine combines six components into overall uncertainty score using hardcoded weights (disagreement 30%, data quality 25%, feature availability 20%, sample size 15%, calibration 10%), but these weights appear arbitrary—no rationale documented, no sensitivity analysis shown, no empirical validation provided.

Market reliability calculator multiplies four weighted factors (probability conviction, calibration status, uncertainty inverse, data quality) into a reliability score that gates betting recommendations, but the formula conflates distinct reliability dimensions without explaining why equal weighting is appropriate.

Smart market selector adds max_uncertainty parameter and uncertainty_assessment parameter but only checks uncertainty_level == 'VERY_HIGH' as string comparison rather than enum comparison, and the overall_uncertainty threshold check lives in _filter_candidates while the level check lives in both filter and pass-reason determination, creating redundant logic paths.

Calibration engine adds CalibrationStatus enum and status property, enforces strict temporal cutoff (< not <=) in fit(), and exposes calibration_sample_size, providing the metadata uncertainty engine needs without changing calibration behavior.

## <details><summary>Issues (8)</summary>

1. **Hardcoded uncertainty weights without justification** — UncertaintyEngine uses weights 0.30/0.25/0.20/0.15/0.10 with no documented rationale, sensitivity analysis, or empirical validation. Either document the reasoning (e.g., domain expert consensus, prior research) or add a comment acknowledging these are provisional pending Group 6 validation. Without justification, reviewers can't assess whether 30% disagreement weight vs 25% data quality weight is reasonable.

2. **VERY_HIGH uncertainty check uses string comparison** — market_selector.py line 445: `if uncertainty_assessment.uncertainty_level == 'VERY_HIGH'` compares against string literal instead of `UncertaintyLevel.VERY_HIGH` enum. This is fragile (case-sensitive, typo-prone) and bypasses type checking. Change to enum comparison: `if uncertainty_assessment.uncertainty_level == UncertaintyLevel.VERY_HIGH`.

3. **Uncertainty level check missing in pass-reason logic** — _determine_pass_reason checks `uncertainty_level in ('HIGH', 'VERY_HIGH')` but _filter_candidates only checks `uncertainty_level == 'VERY_HIGH'`. This asymmetry means HIGH uncertainty triggers a "high_uncertainty" pass reason but doesn't actually filter candidates. Either remove HIGH from pass-reason check (only VERY_HIGH should trigger pass) or add HIGH to filter check (both HIGH and VERY_HIGH filter out). The current split creates misleading diagnostics.

4. **Shot market engine returns empty dict** — predict_all_shot_markets is a complete stub returning `{}` without checking anything. At minimum, verify snapshot contains shot intelligence fields and return unavailability reason when absent. Current implementation silently passes through without indicating why shot markets aren't available.

5. **Distribution selection not implemented** — Shot market engine documents Poisson vs Negative Binomial selection logic ("variance ≈ mean" vs "variance > mean") but _build_team_shots_prediction only reads shot_production.shots_distribution_model string without validating the distribution was actually fit. If ShotProductionCalculator doesn't populate shots_distribution_model, this returns DistributionType.UNAVAILABLE without checking whether distribution fitting failed or was never attempted.

6. **Feature eligibility has no enforcement path** — MarketFeatureSelector extracts eligible features for each market type but no code path consumes this filtered feature set. Models still receive full MatchFeatureSnapshot via ModelOrchestrator.run(). Either wire MarketFeatureSelector into model prediction (models receive filtered features by market) or document that eligibility is advisory for Group 6 feature weight optimization, not runtime filtering.

7. **Market reliability formula lacks justification** — MarketReliabilityCalculator multiplies four factors with weights 0.25/0.25/0.30/0.20. Why is uncertainty weighted 30% but calibration only 25%? Why is probability conviction equal to calibration status? No rationale documented. Either explain the weighting choice or flag as provisional.

8. **Calibration insufficient data threshold inconsistent** — IsotonicCalibration and PlattCalibration both define MIN_SAMPLES = 50, but test_calibration_status.py shows that with 30 samples the status is NOT_FITTED (calibrator refuses to fit) rather than INSUFFICIENT_DATA. The INSUFFICIENT_DATA status only triggers when fitted_sample_size < MIN_SAMPLES AND is_fitted=True, which can't happen because fit() refuses to set is_fitted when n < MIN_SAMPLES. Either lower MIN_SAMPLES and let calibrator fit with warning, or remove INSUFFICIENT_DATA status as unreachable.

### Market feature eligibility mapping

MARKET_FEATURE_ELIGIBILITY defines feature lists for nine markets (1X2, over/under, BTTS, double chance, handicap, team shots, team SOT, total shots, total SOT). Each market maps to 10-30 eligible features. The lists distinguish goal-based features (xG, goals per match, attack strength) for match result markets vs shot volume features (shots per match, shot intelligence) for shot markets vs strength differential features (Elo gap, common opponent delta) for handicap markets.

MarketFeatureSelector._extract_feature_value implements a 60-case switch mapping feature name strings to MatchFeatureSnapshot field paths. Home/away strength features extract from snapshot.home_strength.*, form features from snapshot.home_form.*, league context from snapshot.league_context.*, and advanced features return None with stub comment. All advanced features (team_intelligence_score_*, opponent_adjustment_factor_*, temporal_form_trend_*, lineup_impact_score_*, tactical_matchup_score, shot_intelligence_*) return None because advanced_feature_set extraction isn't wired yet.

get_feature_availability returns FeatureAvailabilityReport with eligible_feature_count, available_feature_count, unavailable_feature_count, availability_ratio, and feature_values dict. This report feeds UncertaintyEngine.assess via feature_availability parameter.

The feature selector is never called by ModelOrchestrator or any model. Models receive the full MatchFeatureSnapshot and extract whatever features they need. Feature eligibility exists as metadata for future Group 6 optimization but doesn't constrain runtime behavior. Documentation should state whether this is intentional (eligibility informs weight selection during backtesting, not runtime filtering) or whether integration is planned.

### Model disagreement extraction

ModelDisagreementResult dataclass holds model_count, available_model_count, mean_probability, probability_std, probability_range, agreement_score (1 = perfect agreement), disagreement_score (1 = high disagreement), model_probabilities dict, agreement_label ("HIGH"/"MEDIUM"/"LOW"/"INSUFFICIENT").

ModelDisagreementAnalyzer.analyze extracts probabilities for a specific outcome (home_win/draw/away_win) from List[ModelPrediction], calculates mean and standard deviation, applies agreement formula `agreement = max(0.0, min(1.0, 1.0 - (std * 3)))`, sets disagreement = 1 - agreement, applies thresholds (HIGH_AGREEMENT >= 0.8, LOW_AGREEMENT >= 0.5).

The formula matches EnsembleEngine._calculate_agreement() exactly, maintaining consistency. The `* 3` multiplier assumes std is measured in probability units [0,1] and scales to agreement range—when std = 0.33, agreement = 0, representing complete disagreement. This is a heuristic (std alone doesn't capture all disagreement patterns like bimodal distributions) but reasonable for ensemble variance quantification.

analyze_all_outcomes calls analyze for home_win, draw, and away_win, returning Dict[str, ModelDisagreementResult]. This provides per-outcome disagreement, allowing uncertainty engine to detect when models agree on home_win probability but disagree on draw vs away_win split.

test_model_disagreement.py verifies high agreement (probabilities 0.45/0.47/0.46 → std < 0.05, agreement > 0.8), low agreement (probabilities 0.60/0.30/0.45 → std > 0.10, agreement < 0.7), single model (returns agreement=1.0, label="INSUFFICIENT"), and all_outcomes returns three results.

### Uncertainty component weighting

UncertaintyEngine.assess multiplies six components by fixed weights: model_disagreement * 0.30 + data_quality_deficit * 0.25 + feature_availability_deficit * 0.20 + sample_size_inadequacy * 0.15 + calibration_uncertainty * 0.10 + probability_dispersion * 0.0.

Each component maps to [0,1] where 0 = no uncertainty, 1 = maximum uncertainty. Model disagreement uses disagreement_score directly. Data quality deficit = 1 - data_quality_score. Feature availability deficit = 1 - availability_ratio. Sample size inadequacy uses sigmoid: `1 / (1 + exp(0.1 * (n - 30)))` targeting n=30 as adequate sample. Calibration uncertainty maps FITTED→0.0, INSUFFICIENT_DATA→0.3, NOT_FITTED→0.5, unknown→0.5. Probability dispersion is optional, currently unused (multiplied by 0.0 in formula, though not in the code—dispersion_component defaults to 0.0 when None but isn't part of the weighted sum because it's not in the formula).

The weights appear arbitrary. Why is model disagreement 30% and calibration only 10%? If calibration maps raw probabilities to true frequencies, shouldn't calibration status weight higher? If sample size determines statistical reliability, why only 15%? No sensitivity analysis shown (what happens if weights shift by ±10%?). No empirical validation (do these weights correlate with actual prediction error on held-out data?).

Comment at line 63-67 says "These weights reflect relative importance but may be adjusted through empirical validation." This acknowledges the weights are provisional but doesn't explain the initial choice. Either document the reasoning (e.g., "30% disagreement based on prior ensemble literature showing inter-model variance dominates other uncertainty sources") or strengthen the comment to "Provisional weights pending Group 6 empirical validation; chosen to emphasize model disagreement (direct prediction uncertainty) over secondary factors."

test_uncertainty_engine.py verifies low uncertainty (disagreement 0.06, quality 0.9, availability 0.95, samples 50, FITTED → overall < 0.3), high uncertainty (disagreement 0.75, quality 0.3, availability 0.4, samples 10, NOT_FITTED → overall > 0.6), medium uncertainty (disagreement 0.4, quality 0.7, availability 0.75, samples 25, INSUFFICIENT_DATA → overall 0.3-0.6). Tests confirm components calculate correctly and thresholds separate LOW/MEDIUM/HIGH/VERY_HIGH (0.3, 0.6, 0.8).

### Market reliability combination

MarketReliabilityCalculator.calculate computes four factors:

1. **Probability factor**: `abs(probability - 0.5) / 0.5` — penalizes low conviction near 50%, rewards extreme probabilities. At prob=0.5, factor=0.0. At prob=0.0 or 1.0, factor=1.0.

2. **Calibration factor**: FITTED=1.0, INSUFFICIENT_DATA=0.7, NOT_FITTED=0.5. Discrete mapping, not continuous.

3. **Uncertainty factor**: `1.0 - overall_uncertainty` — inverse of uncertainty assessment. Low uncertainty (0.2) → factor 0.8. High uncertainty (0.8) → factor 0.2.

4. **Data quality factor**: data_quality_score directly.

Weighted reliability: `0.25 * prob_factor + 0.25 * calib_factor + 0.30 * uncertainty_factor + 0.20 * data_quality_factor`. Thresholds: HIGH_RELIABILITY >= 0.7, LOW_RELIABILITY >= 0.4.

Betting recommendation logic: STRONG_BET requires reliability >= 0.7 AND probability >= 0.65. CONSIDER requires reliability >= 0.5 AND probability >= 0.55. PASS when reliability 0.3-0.5. AVOID when reliability < 0.3.

The formula has architectural issues:

- **Conflating distinct dimensions**: Probability conviction (how strong is the prediction) is conceptually different from calibration quality (are probabilities well-mapped to frequencies) and uncertainty (how much do we trust this estimate) and data quality (is input reliable). Multiplying them assumes they're substitutable—high conviction can offset poor calibration—but these are orthogonal concerns. A 90% prediction (high conviction) on uncalibrated data (poor calibration) should flag both issues, not average them.

- **Equal weighting of conviction and calibration**: Why is probability conviction 25% equal to calibration 25%? If calibration is broken (NOT_FITTED, factor=0.5), that's a structural reliability problem, not equivalent to a 50% probability being uncertain. Calibration failure should veto betting regardless of conviction.

- **Uncertainty already includes data quality**: UncertaintyEngine.assess multiplies data_quality_deficit by 0.25, so data quality contributes to overall_uncertainty. Then MarketReliability multiplies uncertainty_factor by 0.30 AND data_quality_factor by 0.20, double-counting data quality at 0.25*0.30 = 0.075 via uncertainty plus 0.20 direct = 0.275 total, meaning data quality has more influence (27.5%) than any explicit weight suggests.

No rationale documented. Comment at line 65-69 lists weights but doesn't explain them. Either explain why equal weighting is appropriate (e.g., "all four dimensions must pass minimum thresholds independently, so equal weighting reflects equal importance") or restructure as independent gates (calibration MUST be FITTED, data quality MUST be > threshold, then score on conviction and uncertainty).

test_market_reliability.py doesn't exist in the verification.md file list, but a test file should verify the weighting behavior and recommendation thresholds.

### Smart market selector uncertainty integration

market_selector.py adds max_uncertainty parameter to __init__ (default 0.7), uncertainty_assessment parameter to evaluate_and_select (Optional, default None), model_disagreement parameter (Optional, default None), shot_market_predictions parameter (Optional, default None). All new parameters have defaults, preserving backward compatibility.

_filter_candidates adds uncertainty check at line 444-454:

```python
# NEW: Group 5 - Check for VERY_HIGH uncertainty (auto-PASS)
if uncertainty_assessment is not None:
    if hasattr(uncertainty_assessment, 'uncertainty_level'):
        if uncertainty_assessment.uncertainty_level == 'VERY_HIGH':
            # Force PASS with high uncertainty
            return []
    if hasattr(uncertainty_assessment, 'overall_uncertainty'):
        if uncertainty_assessment.overall_uncertainty >= max_uncertainty:
            # Force PASS with high uncertainty
            return []
```

Two issues:

1. **String comparison**: Line 446 compares `uncertainty_level == 'VERY_HIGH'` (string) instead of `== UncertaintyLevel.VERY_HIGH` (enum). This works because UncertaintyLevel is `str` subclass, but bypasses type checking. If UncertaintyLevel enum changes representation, this breaks silently.

2. **Dual check paths**: First checks level == 'VERY_HIGH', then checks overall_uncertainty >= max_uncertainty. VERY_HIGH level threshold is 0.8 (from UncertaintyEngine.HIGH_THRESHOLD), but max_uncertainty default is 0.7. So when overall_uncertainty = 0.75, the level is HIGH (not VERY_HIGH), level check passes, but overall_uncertainty check triggers. This is redundant—either check level or check numeric threshold, not both.

_determine_pass_reason checks uncertainty at line 517-524:

```python
# NEW: Group 5 - Check for high uncertainty first
if uncertainty_assessment is not None:
    if hasattr(uncertainty_assessment, 'uncertainty_level'):
        if uncertainty_assessment.uncertainty_level in ('HIGH', 'VERY_HIGH'):
            return "high_uncertainty"
    if hasattr(uncertainty_assessment, 'overall_uncertainty'):
        if uncertainty_assessment.overall_uncertainty >= 0.6:
            return "high_uncertainty"
```

This checks for HIGH or VERY_HIGH level (string tuple), or overall_uncertainty >= 0.6. The threshold 0.6 matches UncertaintyEngine.MEDIUM_THRESHOLD, so this triggers at the MEDIUM/HIGH boundary. But _filter_candidates only rejects VERY_HIGH (level) or >= 0.7 (numeric). This asymmetry means:

- uncertainty = 0.65 → level = MEDIUM → passes filter → pass_reason = "high_uncertainty" (misleading)
- uncertainty = 0.75 → level = HIGH → passes level check in filter, fails numeric check → pass_reason = "high_uncertainty" (correct but redundant logic)

Recommendation: Simplify to single numeric check. Remove level checks, use only `overall_uncertainty >= max_uncertainty` in filter and pass-reason. This makes behavior predictable (single threshold) and allows users to tune max_uncertainty without worrying about level boundaries.

test cases should verify:
- uncertainty = 0.65, max_uncertainty = 0.7 → candidates NOT filtered
- uncertainty = 0.75, max_uncertainty = 0.7 → candidates filtered, pass_reason = "high_uncertainty"
- uncertainty = 0.85 (VERY_HIGH), max_uncertainty = 0.7 → candidates filtered
- uncertainty_assessment = None → no filtering (backward compat)

### Calibration status tracking

calibration_engine.py adds CalibrationStatus enum (FITTED, INSUFFICIENT_DATA, NOT_FITTED), status property, calibration_sample_size property, get_status_metadata() method.

status property implementation:

```python
@property
def status(self) -> CalibrationStatus:
    if not self.calibrator.is_fitted:
        return CalibrationStatus.NOT_FITTED
    if self._calibration_sample_size < self.calibrator.MIN_SAMPLES:
        return CalibrationStatus.INSUFFICIENT_DATA
    return CalibrationStatus.FITTED
```

Problem: self.calibrator.is_fitted is only True when fit() successfully fits the calibrator. But fit() refuses to fit when len(data) < MIN_SAMPLES:

```python
if len(data) < self.MIN_SAMPLES:
    warnings.warn(...)
    return  # exits without setting is_fitted = True
```

So the second condition (`is_fitted AND sample_size < MIN_SAMPLES`) is unreachable. If is_fitted=True, then sample_size >= MIN_SAMPLES (because fit() won't set is_fitted otherwise). If is_fitted=False, first condition returns NOT_FITTED before checking sample size.

INSUFFICIENT_DATA seems intended for "calibrator was fitted but on borderline data" but current logic makes this impossible. Options:

1. **Lower MIN_SAMPLES and let calibrator fit with warning**: Change MIN_SAMPLES to 30, let fit() proceed when 30 <= n < 50, emit warning, set is_fitted=True. Then status returns INSUFFICIENT_DATA when 30 <= n < 50.

2. **Store sample size before fit attempt**: Store self._calibration_sample_size before the MIN_SAMPLES check, so status can check sample_size even when is_fitted=False. But this changes NOT_FITTED to INSUFFICIENT_DATA retroactively when you call fit() with 30 samples (doesn't fit but marks as insufficient).

3. **Remove INSUFFICIENT_DATA status**: If calibrator refuses to fit below threshold, there's no "fitted but insufficient" state. Collapse to FITTED (>= 50) or NOT_FITTED (< 50).

Current implementation effectively implements option 3 (INSUFFICIENT_DATA unreachable) but keeps the enum value. Either remove it or implement one of the other options.

test_calibration_status.py test_status_after_insufficient_fit creates 30-sample data, calls fit(), expects INSUFFICIENT_DATA, but gets NOT_FITTED because fit() returns early. The test doesn't assert the expected status—it only asserts sample_size=30, which passes. This test doesn't actually verify INSUFFICIENT_DATA is reachable.

Temporal cutoff protection uses strict `<` comparison (line 349: `if ts < cutoff_date`), enforced by comment "# STRICT: Only data BEFORE cutoff_date (< not <=)". test_strict_before_comparison verifies a sample exactly at cutoff_date is excluded. This prevents temporal leakage.
